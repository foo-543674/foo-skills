# 品質の定義と基準

## 製品品質と技術品質

品質には 2 つの種類がある。これらを混同してはならない。

### 製品品質 — 「あったら嬉しい」

その製品のバリュー、セールスポイント。ユーザーが意識的に語るもの。

- アプリのレスポンスが速い
- UI が美しい
- 機能が豊富
- 使いやすい

### 技術品質 — 「なかったら問題」

その製品が当然担保されていると **暗黙的に認知されている** もの。誰も口に出さないのに必須。

- テストが書ける、通る
- リンタが効く、フォーマットが揃う
- CI が回る
- 依存が解決する
- 再現可能な環境で動く
- セキュリティ脆弱性がない
- アーキテクチャの秩序が保たれている

### 優先順位

**技術品質は製品品質に優先する。**

技術品質に Critical な問題が残っている状態で、製品品質の改善に時間を費やしてはならない。セキュリティ脆弱性やデータ損失リスクは、UI の美しさより先に対処する。

これは「技術品質のほうが大事」という意味ではない。技術品質は「当然担保されている前提」であり、その前提が崩れた状態で製品品質を語っても意味がないということ。

## AI 自走時の品質保証: 三層防御

AI に開発の大部分を任せる場合、「AI の判断を信頼する」のではなく「AI の判断を自動検証する」仕組みが必要。

```
Layer 1: CLAUDE.md (ガイダンス)
  AI が従うべきルールを言語で伝える
  → 破れる (AI が複雑な実装中に無意識に違反する可能性)

Layer 2: Architecture Tests (ガードレール)
  ルール違反を CI で自動検出する
  → 破れない (CI が壊れて止まる)
  → ただし AI の資格情報で検証器・保護設定を変えられないときに限る
  → AI 自身が「壊れた → 直す」のループを回せる

Layer 3: Code Review Agent (評価)
  テストでは捉えきれない設計品質を評価する
  → commit / push 前に hook で起動を強制する (手元のレビューゲート)
  → 受け入れの判断材料になる。これで足りる変更は人間に回さない
```

### 人間の確認を「安全側」の既定にしない

**人間に回すのは、人間が責任を引き受ける判断だけ。知識が要るだけの判断は、仕組み・自動化・AI の評価で受け入れる。**

ガードレールを設計するとき、「最終的に人間が見れば一番リスクが低い」と考えて人間の確認を足すのは、安全側に倒したことにならない。

- **人間の確認には費用があり、その費用自体がリスクになる。** 確認の件数・手作業・認知負荷が増えると、人間は中身を見ずに承認するようになり、確認は形骸化する。形骸化した確認は、確認がないより悪い。守られているように見えて、何も止めていないからである。人間に回す項目を足すときは、人間の負荷が増えるという費用と、それで形骸化する確認がどこかを見積もる
- **AI と人間の違いは知識の量ではなく、責任を取れるかどうか。** 判断に要る知識は、もう AI のほうが多いことが多い。「判断する知識はあるが、責任は取れない」を理由に人間に回さない。人間に回すのは、人間が責任を引き受ける判断 (方向性・意図・テイストの決定、リスクの受容、金銭、外部への約束、取り消せない外部への作用、基準の改訂) と、人間にしかない情報 (語られていない意図、事業上の前提) が要る判断に限る
- **仕組み → AI の評価 → 人間、の順に考える。** まず決定的ゲートや保護された検証器で確かめられる形にする (変更を分ける、構造化する、テストを足す)。次に独立した AI のレビューで評価する。それでも残り、かつ上の責任か情報が要る部分だけを人間に回す
- **人間に回す項目には、人間が見て何を引き受けるのかを書く。** 「重要だから」「影響が大きいから」「念のため」「安全側に倒した」は理由にならない。書けないなら、その項目は人間に回さない

人間の確認を減らすことは、AI の判断を検証しないことではない (上の三層防御)。検証は仕組みと AI の評価に寄せ、人間は責任を引き受けることに集中する。

### Architecture Tests で検証すべきルール

- **依存方向**: domain が infrastructure を import していないか
- **型の配置**: ORM 型がドメイン層に出現しないか
- **命名規則**: 禁止語 (Service, Manager 等) がクラス名に使われていないか
- **import 制限**: ガイドラインで定めた制限が守られているか

これらは perspectives/ の品質基準から導出し、プロジェクトの技術スタックに応じたツール (dependency-cruiser, ArchUnit, import-linter 等) で実装する。
