# 品質の定義と基準

## 製品品質と技術品質

品質には 2 つの種類がある。これらを混同してはならない。

### 製品品質 — 「あったら嬉しい」

その製品のバリュー、セールスポイント。ユーザーが意識的に語るもの。

- アプリのレスポンスが速い
- UI が美しい
- 機能が豊富
- 使いやすい

### 技術品質 — 「なかったら問題」

その製品が当然担保されていると **暗黙的に認知されている** もの。誰も口に出さないのに必須。

- テストが書ける、通る
- リンタが効く、フォーマットが揃う
- CI が回る
- 依存が解決する
- 再現可能な環境で動く
- セキュリティ脆弱性がない
- アーキテクチャの秩序が保たれている

### 優先順位

**技術品質は製品品質に優先する。**

技術品質に Critical な問題が残っている状態で、製品品質の改善に時間を費やしてはならない。セキュリティ脆弱性やデータ損失リスクは、UI の美しさより先に対処する。

これは「技術品質のほうが大事」という意味ではない。技術品質は「当然担保されている前提」であり、その前提が崩れた状態で製品品質を語っても意味がないということ。

## AI 自走時の品質保証: 三層防御

AI に開発の大部分を任せる場合、「AI の判断を信頼する」のではなく「AI の判断を自動検証する」仕組みが必要。

```
Layer 1: CLAUDE.md (ガイダンス)
  AI が従うべきルールを言語で伝える
  → 破れる (AI が複雑な実装中に無意識に違反する可能性)

Layer 2: Architecture Tests (ガードレール)
  ルール違反を CI で自動検出する
  → 破れない (CI が壊れて止まる)
  → ただし AI の資格情報で検証器・保護設定を変えられないときに限る
  → AI 自身が「壊れた → 直す」のループを回せる

Layer 3: Code Review Agent (評価)
  テストでは捉えきれない設計品質を評価する
  → commit / push 前に hook で起動を強制する (手元のレビューゲート)
  → 受け入れの判断材料になる。これで足りる変更は人間に回さない
```

**常に読ませる規則 (Layer 1) は最小に保つ。** 規則は足すほど 1 つ 1 つが薄まり、効かなくなる。規則を足すときは既存の記述と統合して総量を増やさず、定期的に統合・刈り込みをする。守らせたいことは、まず Layer 2 以上 (仕組みで止める) に置けないかを問う。

### 人間の確認を「安全側」の既定にしない

**人間に回すのは、人間が責任を引き受ける判断だけ。知識が要るだけの判断は、仕組み・自動化・AI の評価で受け入れる。**

ガードレールを設計するとき、「最終的に人間が見れば一番リスクが低い」と考えて人間の確認を足すのは、安全側に倒したことにならない。

- **人間の確認には費用があり、その費用自体がリスクになる。** 確認の件数・手作業・認知負荷が増えると、人間は中身を見ずに承認するようになり、確認は形骸化する。形骸化した確認は、確認がないより悪い。守られているように見えて、何も止めていないからである。人間に回す項目を足すときは、人間の負荷が増えるという費用と、それで形骸化する確認がどこかを見積もる
- **AI と人間の違いは知識の量ではなく、責任を取れるかどうか。** 判断に要る知識は、もう AI のほうが多いことが多い。「判断する知識はあるが、責任は取れない」を理由に人間に回さない。人間に回すのは、人間が責任を引き受ける判断 (方向性・意図・テイストの決定、リスクの受容、金銭、外部への約束、取り消せない外部への作用、基準の改訂) と、人間にしかない情報 (語られていない意図、事業上の前提) が要る判断に限る
- **仕組み → AI の評価 → 人間、の順に考える。** まず決定的ゲートや保護された検証器で確かめられる形にする (変更を分ける、構造化する、テストを足す)。次に独立した AI のレビューで評価する。それでも残り、かつ上の責任か情報が要る部分だけを人間に回す
- **人間に回す項目には、人間が見て何を引き受けるのかを書く。** 「重要だから」「影響が大きいから」「念のため」「安全側に倒した」は理由にならない。書けないなら、その項目は人間に回さない

人間の確認を減らすことは、AI の判断を検証しないことではない (上の三層防御)。検証は仕組みと AI の評価に寄せ、人間は責任を引き受けることに集中する。

### Architecture Tests で検証すべきルール

- **依存方向**: domain が infrastructure を import していないか
- **型の配置**: ORM 型がドメイン層に出現しないか
- **命名規則**: 禁止語 (Service, Manager 等) がクラス名に使われていないか
- **import 制限**: ガイドラインで定めた制限が守られているか

これらは perspectives/ の品質基準から導出し、プロジェクトの技術スタックに応じたツール (dependency-cruiser, ArchUnit, import-linter 等) で実装する。

## 致命的な失敗とガードレール

**守る対象は致命的な失敗だけにする。** AI は「融通は利かないが、知識が豊富で作業の速い人」として扱う。その人が致命的な失敗をしない環境・ルール・ガードレールを設計し、それ以外の失敗は防がずに、起きたら速く直す。

「人間が判断するから安全」は成り立たない (上の「人間の確認を『安全側』の既定にしない」)。AI がオーナーの GitHub アカウントを操作すること、自動でマージすること、AI が自分の振る舞いやコンテキストを書き換えることは、それ自体を損失として扱わない。

設計は STPA (System-Theoretic Process Analysis、Nancy Leveson) の順で行う: 受け入れられない損失 → 損失につながる危険な状態 → 危険な状態を避ける制約 → 制約を守らせる仕組み。

### 受け入れられない損失

| # | 損失 | 承認で受け入れられるか |
|---|---|---|
| ① | セキュリティの穴を作る | 承認の有無にかかわらず防ぐ |
| ② | 情報を漏らす | 承認の有無にかかわらず防ぐ |
| ③ | 承認なしに、決済してお金を使う | オーナーの承認があればよい |
| ④ | 承認なしに、バックアップの無い削除をする | オーナーの承認があればよい |
| ⑤ | 承認なしに、オーナーの名義で外へ発信する | オーナーの承認があればよい |

- **④の理由**: データは資産である。バックアップの無い削除は、そのデータを最初から無かったことにするのと同じ
- **⑤の理由**: 外に向けた発信は、オーナーが責任を取れるかを判断する前に止まらない
- **③〜⑤の承認は、安全のためでなく責任の引き受けのためにある。** 上の「人間に回すのは人間が責任を引き受ける判断 (金銭、外部への約束、取り消せない外部への作用)」と同じ線である。①②は、誰かが責任を引き受ければ済むものではないので、承認があっても防ぐ

**損失に当たらない失敗は防がない。** 起きたら再発防止で直す。取り返しがつく失敗 (引き返せる扉) は速く進めて直し、取り返しがつかない失敗 (引き返せない扉) だけを事前に止める。損失に当たらないものまで事前に止めると、守りの手間が作業を際限なく遅くし、守り自体が形骸化する。

### 危険な状態と制約

洗い出しの起点。生成先の目的 (開発、相談、創作など) に合わせて足す。

| 損失 | 危険な状態 | 制約 |
|---|---|---|
| ① | 公開範囲を広げる、保護 (ruleset・セキュリティ設定) を外す、権限やトークンのスコープを広げる、秘密をコード・ログに書く | AI の手が届く認証に管理系の権限を載せない。秘密は AI が書き込めるもの (コード・ログ) に渡さない。commit・push の関門は、既知の形の秘密を捕まえる補助として置く (AI が変えられる手元の検査は強制にならない) |
| ② | 秘密の値を読んで会話や外部に出す、非公開のデータを外部サービス (Web 検索・別の AI・外部 API) に送る、公開リポジトリに私的な情報を push する | 秘密の値は AI が読めない場所に置き、扱うのは名前・更新日時などのメタデータまでにする。送り先を限る |
| ③ | 有料サービスの契約・購入、従量課金のリソースの作成、API の大量呼び出し | AI の手が届く認証に支払い手段・課金の権限を載せない。従量課金には上限を置く |
| ④ | リポジトリ・ブランチ・データの削除、force push・履歴の書き換え、復元できない上書き | 消せる権限を載せない。消すときは承認を取る。既定は復元できる形での退避 |
| ⑤ | SNS・メール・チャットへの送信、他人のリポジトリへの Issue・コメント・PR | AI は下書きまで。送信は承認を取る |

### 守らせる仕組み

強い順に選ぶ。上の段で守れるなら、下の段に頼らない (三層防御と同じ向き)。

1. **権限を最初から持たせない**: AI の手が届く認証に、危険な状態を作れる権限が載っていない。AI が誤っても、意図しても、その操作は失敗する
2. **関門で止める**: hook (git hook・AI ツールの hook) や CI の検査が、危険な操作を実行の直前で止める
3. **規則に書く**: AGENTS.md 等に書いて AI に守らせる。破れるので、上の 2 段が取れないときだけにする

### 端末の認証 — AI と共用する認証から致命的な権限を外す

守る対象は「誰が操作したか」ではなく「どんな操作ができるか」である。オーナーの日常の認証から致命的な権限を外し、その認証を AI と共用する。AI とオーナーの作業場所を分ける必要はない (分けると、検証のたびにオーナーが手元で pull する手間や、作業場所に無いコマンドを組み直す手間が出る)。

これが成り立つのは、**AI の手が届く認証のすべて** が上の制約を満たすときに限る。GitHub のトークンだけでなく、同じ端末にある SSH 鍵と ssh-agent、git の credential helper、クラウドやパッケージレジストリの CLI の認証、ブラウザのログイン状態、AI ツール自身の API キーも数える。致命的な権限を持つ認証は、AI が使えない場所 (別の OS ユーザー、パスワードマネージャ、使うたびの対話的な認証) に置く。

GitHub での形:

- **日常の認証は、権限を細かく絞れるトークンにする。** 手元の gh・git が使うトークンを fine-grained personal access token にし、Administration と Deployments: write を載せない。リポジトリの削除・設定の変更 (公開範囲の変更を含む)・ruleset の変更と削除には Administration: write が要り、pending deployments の承認には Deployments: write が要る。管理の操作はオーナーがブラウザで行う
- **マージの関門は CI の検査にする。** 認証を共用するので、PR の作成者と承認者が同じアカウントになる。GitHub は PR の作成者による承認を認めないので、「オーナーの承認が要る」という保護はかけない。オーナーの承認は、損失③〜⑤に当たる操作にだけかける
- **既定ブランチの force push と削除を ruleset で禁止する。** 消えると戻せないもの (リリースに使うタグ等) があれば、それも ruleset の対象にする。Administration の無いトークンでは、この ruleset を変えられない。ただし、変えられないことと迂回できないことは別である。ruleset の迂回を許す主体 (bypass) にオーナーを常時の形で入れない。bypass に入った主体の迂回が、Administration の無いトークンでの push にも効くかは未確認なので、実際のトークンで force push が拒否されることを確かめる
- **workflow から届く秘密を、漏れても致命的でないものに限る。** Workflows: write があれば、AI は workflow を書き換えて、リポジトリの secrets と `GITHUB_TOKEN` を使える。致命的な権限を持つ認証はリポジトリの secrets に置かず、下の Environment に置く。`GITHUB_TOKEN` の既定の権限は読み取りにする。Environment を使うジョブを自己ホストの runner で動かさない (前のジョブが runner に残したものが、承認済みのジョブに干渉できる)
- **管理権限が要る設定をコードで管理するなら、適用は CI で行う。** 差分を見る (plan) のは手元、適用 (apply) は main へのマージ後に CI で行う。管理権限の認証は GitHub の Environment のシークレットに置き、Environment の承認者 (required reviewers) をオーナーにする。承認が通るまで、ジョブはシークレットを読めない。手元のトークンに Deployments: write が無いので、承認はオーナーがブラウザで押す。Environment の「Prevent self-review」は付けない (承認を求めるジョブを起こしたのはマージしたオーナーのアカウントなので、付けるとオーナーも承認できなくなる)。管理者は既定で Environment の保護を迂回できるので、公開リポジトリでは「Allow administrators to bypass configured protection rules」を外す。外せないときは、Deployments: write の無いトークンでは迂回できないことを実際に確かめる (未確認)

残る穴とその扱い (オーナー合意済み): AI が適用のワークフロー自体を書き換えて main にマージすると、承認の後に書き換えた処理が管理権限で動く。特定のルールの変更なのにワークフローのファイルが変わっていたら、オーナーが承認の前に見る。見逃したときは戻す。

プランによる制限 (GitHub の公式ドキュメントで 2026-11-22 に確認): GitHub Free では、ruleset、Environment (シークレットと承認者を含む)、Environment の保護を管理者が迂回できないようにする設定は、公開リポジトリでしか使えない。Free の private リポジトリでは、上の ruleset と Environment による守りが成り立たない。既定ブランチの force push と削除は Contents: write で行えてしまい、管理権限の認証を CI に置く形も作れない。その場合は、守れていないことを記録し、プランの変更・公開範囲の変更を選択肢として示す。
