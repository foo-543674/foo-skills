# 技術選定の判断基準

私が技術を選ぶとき、何を重視し、どういう傾向があるかを記述する。AI はこれを参照して技術提案を行う。

## 型システムへの信頼

**静的型付けを強く好む。** やろうと思えば動的型付けスクリプト言語でサクッと開発できるが、私の思想としてそうは思わない。

### なぜ静的型付けか

- **型は設計意図の表現**: 「未検証 / 検証済み」「ID / 生文字列」を型で区別することで、コンパイル時に設計意図の違反を検出できる
- **Result/Either でエラーを表現**: 例外に頼らず、型レベルで「失敗しうる操作」を明示する。呼び出し側がエラー処理を忘れることをコンパイラが防ぐ
- **リファクタリングの安全性**: 型があることで、大規模な構造変更をコンパイラに守られながら実行できる

### 選定傾向

- バックエンド: Rust, Scala, Kotlin, Go。TypeScript はバックエンドには使わない
- フロントエンド: TypeScript (strict mode 必須)、Flutter にも関心がある
- スクリプト/CLI: 言語そのものより **「どこで走らせるか」と「準備なしに実行できるか」** が重要。CLIツールを叩こうとしたら npm がインストールされていない、バージョンが違う — こういう状況を避けたい。GAS なら JS 一択、Lambda や GitHub Actions ならランタイムの制約に従う。実行環境が言語を決める
- 動的型付け言語を選ぶのは、実行環境の制約がある場合のみ

## プログラミングパラダイム

**関数型プログラミングを好む。** ただし純粋な関数型言語を使うという意味ではなく、実用的な言語の中で関数型の考え方を適用する。

### なぜ関数型か

高階関数と型システムによる **表現力** にある。手続き型言語では表現できない「英文法」のような構造を扱え、英文を書くように宣言的に読みやすいコードをシンプルに書ける。命令の羅列ではなく「何を求めているか」が読み取れるコードになる。

### 重視すること

- **Immutable ファースト**: データの変更ではなく新しいデータの生成
- **Pure functions の優先**: 副作用を最小限に抑え、テスタビリティを上げる
- **関数合成**: パイプライン的なデータ変換。英文のように左から右へ読める
- **型による状態遷移の表現**: Union types / sealed class でドメインの状態を表現
- **宣言的なスタイル**: 「どうやるか」ではなく「何であるか」を書く

### 避けること

- 最上部での変数一括宣言
- Mutable なコレクションの多用
- C 言語スタイルのループ (map/filter/reduce で書けるもの)
- 破壊的な操作の連続

## 実行環境 — 言語のツールチェーンは作業環境に入れない

**人と AI が作業する環境 (ホスト、AI を動かすコンテナ等) には、プロジェクトの言語ツールチェーンを入れない。** 言語のコマンド (`cargo` / `pnpm` / `go` 等) は、プロジェクトが定義する開発イメージの中で走らせる。

- **なぜ**: 版がプロジェクトに固定され、誰の環境でも同じ結果になる。作業環境が汚れない。AI の実行環境をプロジェクトのスタックから独立させられる (スタックごとに AI の箱を作り直さない)
- **いつ**: 開発コマンド・git hook・AI が叩く検証コマンドのすべて。CI も同じ開発イメージを使う
- **「コマンドが見つからない」とき**: 作業環境にインストールする、直接叩く方法を探す、のどちらもしない。入口 (開発イメージ経由でコマンドを走らせる仕組み) が無い・壊れているのが原因なので、そちらを直す

### 開発イメージに入れるもの、clone したままで動かすもの

開発イメージに閉じ込めるのは **プロダクトを作るコマンド** (ビルド・テスト・lint・型チェック) だけ。**リポジトリを扱う仕組み** — git hook と Claude Code hook それ自身の処理 (対象の判定、レビュー記録の確認、差し戻し)、開発コマンドの入口 — は、clone しただけのホストにあるもの (git と POSIX シェル。入口を呼ぶときだけ docker / podman) で動かす。Node・Python・jq やプロジェクトの言語で書かない。

- **なぜ**: 開発イメージに入れるのは「ホストに入れたくないから」であって、開発環境を立ち上げないとリポジトリに触れなくするためではない。clone して少し動かしてみる、commit / push する、動かないときにホストの AI に調べてもらう — この入口で開発環境の起動を求めると本末転倒になる
- **前提にしてよいのは git とコンテナ環境まで**: docker / podman があれば、clone した直後に手作業の準備 (依存の install、ツールの導入、開発環境の起動) なしで commit / push まで通る。ゲートが要るもの (依存・イメージ) はゲート自身か入口が用意する。「先に `pnpm install` して」のように準備不足で止めるのは、品質ではなく手順で止めていることになる。少しテキストを直して、確認は CI に任せて push する、という使い方を準備の要求で妨げない
- **ゲートが止めるのは変更の品質**: ゲートは誰が書いても品質を一定にするためのもので、人にも AI にも同じようにかかる。止めてよいのは変更が基準を満たさないときで、作業者の環境の準備が足りないときではない
- **ゲートの範囲**: 開発イメージが必要な決定的ゲートは、それが守る操作 (commit / push) だけを止める。仕組みの一部が動かないことを理由に、対象外の操作 (ホストの AI の調査用のコマンドやファイル編集) まで止めない
- **AI の実行環境はプロジェクトの前提ではない**: ai-box はオーナーが AI 開発をするための個人の環境。生成するリポジトリは、clone した誰もが ai-box の外で使う前提で作る。「ai-box には Node があるから Node で書く」のように、特定の作業環境にあるものを仕組みの前提にしない

## アーキテクチャの判断傾向

- **レイヤードアーキテクチャ**: 営みの起源でレイヤーを分ける (perspectives/architecture 参照)
- **テストファースト**: Red-Green-Refactor サイクル
- **CQRS**: 書き込みと読み取りで要求が異なる場合のみ。過剰適用しない
- **DDD**: ドメインモデルの語彙を大事にする。ただし戦術パターンの形式的な適用は避ける

## 選定プロセス

技術選定時に検討する軸:

1. **要件を満たせるか** (機能要件 + 非機能要件)
2. **型システムの強さ** (静的型付け + 型推論の質)
3. **コミュニティの成熟度** と長期サポート
4. **既存スタックとの整合性**
5. **捨てやすさ** (隔離戦略が適用できるか)

トレードオフが発生した場合は ADR に記録する。
