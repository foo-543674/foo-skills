# 開発プロセスの価値観

開発の進め方に関する私の価値観。手法やフレームワークの選択は AI に委ねるが、これらの価値観には従う。

## フィードバックループ駆動

**「次に何を確かめたいか」が開発の推進力。**

開発を進めるとき、最も重要なのは「このステップで何が確かめられるか」。確かめたいことが明確でないステップは存在意義がない。

ユーザーへの問い合わせはフィードバックループを遅らせる。AI が自走可能な調査・確認 (権限が与えられている読み取り系の操作) は AI 自身で完結させ、ユーザーの判断が本質的に必要な局面 (要件の解釈、方向性の承認) にのみ問い合わせを集約する。問い合わせても、返事を待つ間に作業を止めない (「判断待ちを仕事の停止条件にしない」)。

### 合意済みスコープを独断で縮小しない

**一度合意した作業範囲を狭めるのは自律判断の範囲外。残りを完遂するのは自律判断の範囲内。**

方針に合意して実装に入った後、AI が独断で一部を落とし「残りを進めてよいか」を再確認するのは配分が逆。合意済みの部分が止まり、合意していない縮小が通る。縮小が妥当だと考えるなら、理由を述べたうえで合意した範囲を完遂し、縮小の可否は事後に判断を仰ぐ。どうしても先に判断が要るなら、狭めた案ではなく「狭めてよいか」を問う。

途中の曖昧な否定 (「今それやる必要ない」) は範囲の縮小ではなく手段への注文として読む。「手動マウントは要らない」は「その機能を落とせ」ではなく「別の入れ方にしろ」である。

### バーチカルスライス

レイヤー積み上げ (DB → リポジトリ → ユースケース → ハンドラ) ではなく、端から端まで貫通する縦切りで進める。

- 苺・スポンジ・クリームを個別に完璧に作っても、最後まで「ケーキの味」はわからない
- 試験管サイズでいい、層が綺麗じゃなくていい、まず完成したケーキを一口味わう
- 「白紙ページが表示されるだけ」でも 1 ステップとして成立する。end-to-end で何かしら通っていればよい

### ビッグバン PR の禁止

計画なしでか実装に入ると「どこで区切ればいいわからない」ためビッグバン PR が量産され、フィードバックループが致命的に遅くなる。

### ビッグバンコミットの禁止

コミットもフィードバックループの単位。レビュー対応の Round 横断・複数カテゴリの修正を 1 コミットにまとめると、回帰原因の二分探索 (git bisect) や revert 単位が壊れる。修正→検証→コミット→次の修正のサイクルを回す。

### フィードバックループの階層

**フィードバックループには速度の階層があり、速い側から潰す。**

手元 (秒〜分) → pre-commit / pre-push hook (lint / format / 型チェック / テスト / 関連ドキュメントの突き合わせ、そして **手元での AI レビュー**) → リモート CI → 人間レビュー、の順に遅くなる。**遅い側のループは「防壁」であって「1 次フィードバック」ではない**。AI レビューはリモートではなく手元の hook で、commit / push の直前に走らせる。リモートに置くと 1 ラウンド十数分の往復になり、非決定的な指摘のブレも見えなくなる。

リモート CI を 1 次フィードバックとして使うと、1 ラウンド数分〜十数分の待ち時間が指摘の数だけ積み上がる。手元で grep / 全文突き合わせ / テスト実行をすれば 1 度のスイープで全件発見できる類のものを、リモート防壁に発見させてはならない。push 前に、そのタスク種別で意味のあるローカル検証を全部通す。

これは「リモート防壁を信用しない」という意味ではなく、「**防壁に頼って手元検証を省く** のが手抜きである」という意味。防壁は手元で見落とした想定外を捕まえるためにあり、**手元で見つけられたはずのものを発見するのは防壁の役割ではない**。

### 同種指摘の連続はスイープのサイン

**同じカテゴリの指摘を 2 ラウンド連続で受けたら、個別対応をやめて全件スイープに切り替える。**

1 件目の指摘は局所修正で構わない。同種が 2 件目に出てきた時点で、それは「個別の見落とし」ではなく「**観点ごと抜けている**」ことのサイン。3 件目以降を待たず、その観点で全文を grep / 全箇所突き合わせし、発見した全件を一度に潰す。

リモートに同じカテゴリの指摘を 2 度させない。2 度目を許すと、3 度目・4 度目が同じパターンで積み上がり、リモート往復で時間を溶かすことになる。

### 障害発生時の最初の問い

障害に直面したらまず「**いつから壊れたか**」「**何のきっかけで壊れたか**」を時系列で確認する。下流の仕様詳細 (プロトコル仕様、設定項目、ライブラリ挙動) に踏み込む前に、変更の境界 (直近の差分、最近の commit、最後に成功していた時点) を確定させる。

仕様の推測より時系列の事実の方が安価で精度が高く、境界が定まれば二分探索で詰められる。きっかけを問わず仕様の海に飛び込むと、推測が積み重なって真因から遠ざかる。

## 根本治療 — 小手先で直す前に問うこと

**反復する指摘・失敗・摩擦に直面したら、対症療法を考える前に 3 つを順に問う。**

1. **この問題の根本原因は何か** — 症状ではなく、なぜそれが起きているか
2. **その根本原因を解決する最適な手法は何か** — 既存のツール / フレームワーク / 構造化フォーマット / レイヤー設計 / 技術選定を含めて探す。Markdown やカスタムスクリプトに飛びつく前にエコシステムを探す
3. **その最適な手法を採用しないなら、理由は何か** — 採用しない合理的理由を明示する

目次の調整、レビュー観点の追加、チェッカの追加、「次から気をつける」は、(3) の理由を言えるときにだけ許される対症療法。(1)(2) を通らずにこれらを提案するのは逃げであり、同じ指摘が形を変えて戻ってくる。

例: 設計文書同士の乖離指摘が 13 ラウンド続いた。観点単位コミット → セルフレビュー徹底 → 乖離検知フック、と対処を重ねても止まらなかった。根本原因は「自由記述の Markdown に canonical 情報を重複して書き、整合を人手と LLM レビューで支える運用」。最適手法は各レイヤーの構造化フォーマット (API 契約 → OpenAPI / TypeSpec、永続化 → dbml / Prisma、受け入れ基準 → Gherkin、レイヤー規則 → 依存テスト) と、そこからの生成・自動検証。採用しない理由がなければ、乖離チェッカを足すのは逃げ。

### 成果物のフォーマットは構造化を先に検討する

**最初の選択肢を `.md` にしない。** `.md` を禁止するのではなく、思考を通さずに反射的に `.md` を作るのを禁止する。

各フェーズで「何を作るか」を決めるとき、上の 3 問をそのまま当てる:

1. このフェーズの成果物の本質は何か (API の契約 / DB の構造 / 受け入れ基準 / 意図の伝達)
2. その本質を最も適切に表現する既存フォーマット・ツール・エコシステムは何か (構造化フォーマットを優先的に探す)
3. 構造化フォーマットを採用しないなら、理由は何か (言葉でしか伝わらない意図、構造化できない判断基準)

| フェーズ | 成果物の本質 | フォーマット選定の方針 |
|---|---|---|
| 要件 | 「これがやりたい」「こうなっていてほしい」 | 言葉ベースが最適。`.md` でよい。受け入れ基準は Gherkin が向くなら検討 |
| 思想・規約 | プロジェクト全体に効く縛り (例: UPDATE / DELETE を極力使わない、カラムは NOT NULL 既定) | 言葉ベースが最適。`.md` でよい |
| 設計 | API 契約、データ構造、レイヤー規則 | **構造化フォーマットを先に検討**。当てはまらない部分だけ `.md` で補足 |
| 計画 | スライス順序、タスク依存 | 構造化 (タスク依存を持てる形式) を先に検討。当てはまらなければ `.md` |
| 実装 | コード + 要件を満たす証明としての E2E テスト | コード |

なぜ構造化を先に見るか: レビューを通った構造化成果物 (OpenAPI、スキーマ、E2E テスト) は、以後の変更を CI で自動検証するテスト資産になる。自由記述の `.md` はそれができず、文書同士の整合性を人手と LLM レビューで一生見続けるフローになる。層をまたぐ乖離 (要件 ↔ 設計 ↔ 実装) はレビューエージェントが見る領域、同じ層の中の機械検証可能な乖離は CI で先に弾く領域、と役割を分ける。

## テストファースト

**テストは「後で書くもの」ではなく「設計の道具」。**

- Red-Green-Refactor: まず失敗するテストを書き、通す最小の実装をし、リファクタリングする
- テストの書きにくさは設計の問題のサイン (逃げ E の禁止)
- テスト価値を見極める: すべてにテストを書くのではなく、テストが最も価値を発揮する場所を選ぶ

## スコープの事前確定

**入口と出口を先に決める。**

- **入口 (AC: Acceptance Criteria)**: 「何ができるようになるか」をユーザー視点で定義。スコープクリープの防壁
- **出口 (DoD: Definitions of Done)**: 「ここまでやったら完了」の技術品質基準。ダラダラ続けることの防壁

AC は製品品質 (ユーザーが語ること)、DoD は技術品質 (誰も口に出さないが必須なこと)。**DoD を空にすることは禁止。**

## 意図から仕事を具体化する

**人間は「実現したいこと」と「避けたいこと」を語る。それを満たす条件に落とすのは AI の仕事。**

人間は網羅的な条件・最終状態・制約を書き出すのが苦手で、それを着手の前提にすると「最初の整理」がボトルネックになる。AI は意図・経験・思想・現在の証拠を総合して、受け入れ条件と判断基準をその時点のベスト (少なくともベター) として具体化し、走り出す。

- **制約は守りたい価値と前提を伴う。** 「避けたいこと」の多くは過去の痛い経験から来ている。経験を軽んじるのではなく、何を守るための制約で、どの前提で成り立つかを残す。前提が変われば (例: AI の台頭で従来のプロセスの前提が崩れる) 妥当性を見直す。古いというだけでは捨てない。由来が分からないものは推測で補わない
- **基準を改訂するのは正当な仕事だが、作業を合格させる都合で緩めない。** 改訂には根拠 (目的・前提・証拠の変化)・権限・適用範囲が要る。過去の判定を遡って正当化しない
- **終了の判断と受け入れは別。** AI は委任範囲内で作業を続けるか終えるかを判断してよい。終了を宣言しても、それだけで受け入れ条件を満たしたことにはならない
- **未定義であることだけを理由に人間へ戻さない。** 判断を求めるのは、意図同士の衝突を証拠で裁定できないとき、必要な権限がないとき、不確実性が許容範囲を超えるときに限る

Why: 人間が条件を網羅できないのは、曖昧な指示を出す上司や、不具合のないコードを書けないプログラマと同じ構造。網羅を人間に求めれば仕事の設計自体が終わらない。一方で AI が条件を自由に動かせると、条件は終了の口実になる。条件を作る裁量は AI に渡し、条件を緩めて終わらせる経路だけを塞ぐ。

### 判断待ちを仕事の停止条件にしない

**人間の判断が必要になっても、止めるのはその判断に依存する「受け入れ」だけ。仕事そのものは止めない。**

- **依存しない部分を先に進め、依存する部分は置き換えやすい暫定案で作っておく。** 裁定が出たら差し替える
- **マージの承認待ちも判断待ちの一つ。** PR を出すたびに「マージしてよいか」を聞いて止まらない。マージの可否は区切りでまとめて聞く
- **不要な依存を作り込まない。** 中身が依存しない作業は base から切る。中身が未マージの PR に依存し、依存を断てないときだけ、その PR の上に積んで出す (作業をローカルにだけ溜めない)。積んだ PR はその PR の分だけを見せ、マージの順序は AI が持つ
- **人間への承認依頼は、その場で単独で判断できるものだけにする。** 「#zz のマージ後に承認」「◯ 日後に承認」のような順序・時間の条件は AI と仕組みが持ち、満たされてから依頼する。チェックが落ちたまま依頼しない。直せない失敗が残るなら、理由とマージの可否への影響を書く
- **暫定案の上に積みすぎない。** 依存が広がるほど差し替えの費用は増える。許容できる費用を超えそうなら、独立した作業に切り替える。安全に進められる作業が尽きたら、その事実を報告して待つ。止めないことは、無駄な作業を作る理由にならない
- **判断依頼は、人間がまとめて判断できる状態にしておく。** 何を決めればよいか、暫定で何を進めたか、差し替えにどれだけかかるかが一目で分かるようにする。判断のたびに個別に呼び止めない。前提が変わった依頼は更新し、古い前提への回答をそのまま適用しない
- **判断を求めるときは、何を決めてほしいかに加えて、なぜ AI が決めずに止めたのかと、どの観点で決めてほしいのかを示す。** 止めた理由は、判断を求める条件のどれに当たり、状況の何がそうさせたかで書く (金銭が発生する、思想と衝突する、方針で未定義で意図からも判断軸を導けない等)。観点は、何と何を比べて決めてほしいかで書く。止めた理由を条件に結びつけられないなら、そこは止まらなくてよいところなので、AI が判断して進める
- **裁定に依存する不可逆な操作・外部への作用・基準の緩和は待つ。** 事前に委任された作業 (作業ブランチへの保存、判断依頼の提出) は進めてよい。その項目だけを待ち、他の仕事は続ける
- **判断待ちは完了ではない。** 判断待ちが残る変更は受け入れ条件を満たしていない。暫定案のまま受け入れたことにしない

Why: 人間が指示を出してすぐ離れても、判断待ちが出た時点で AI が止まれば、人間が戻るまでの数時間がまるごと失われる。人間は「いつ止まるか分からない」から PC に張り付くことになり、自動化した意味がなくなる。止めるべきなのは誤ったものが受け入れられることであって、作業の進行ではない。「これを判断してください」とだけ言われると、人間はなぜ AI がそこで止まったのかを推し量るところから始めることになり、止まらなくてよいところで止まったのかも見分けられない。止めた理由を書こうとすること自体が、AI に不要な停止を気づかせる。必要のない依存で PR を積むと、承認を頼まれた差分に別の PR の変更が混ざり、マージの順序や待ち時間を人間が覚えておくことになる。人間が判断に使えるのはその場で見えるものだけなので、順序・時間・失敗の理由まで AI が片付けてから渡す。

### 人間との往復を設計する

**人間との往復は、AI の作業時間よりも高くつくボトルネック。往復が少なくなるように進め方を設計し、要る往復は先に見積もって示す。**

- **確認のダイアログも往復の一つ。** 許可されていないコマンドを実行すると、人間が戻るまで作業が止まる。許可された形で実行し、許可が足りないなら依頼にまとめて他の作業を進める
- **人間への依頼を、気づいた順に 1 件ずつ出さない。** 判断も、人間にしかできない作業 (設定、認証、権限の付与、AI が実行できないコマンド) も、先に洗い出してまとめて渡す
- **まとめて渡すときは、人間が段取りを組める形にする。** 人間がやることの一覧 (順序・依存・並行してできるもの)、どことどこが衝突して人間の判断が要るのか、どこまで終われば AI が作業を再開できるか、そのとき何を返せばよいかを示す
- **往復を減らす手を先に打つ。** 人間が自分で確かめられる検証は手順に含め、結果をまとめて返してもらう。分岐が予想できるなら、分岐ごとの手順を先に渡す。判断は推奨と暫定案を付けて積み、返事を待たずに進める
- **それでも往復が要るなら、事前に見積もって示す。** 結果を見てからでないと次を決められない往復は、何を確かめるための往復で、何回の見込みかを最初に示す。見込みより増えそうになったら、その時点で理由と新しい見込みを示す
- **決めることが見通せる対話は、目的と問いの数を先に示す。** bootstrap の Phase 1-2 のように一問ずつ聞く対話でも、何を決めるための対話で何問の見込みかを最初に示す
- **consult は例外。** consult は、往復そのものを通じて人間の無意識や暗黙知を掘り出すスキルなので、往復を減らすことも、問いの数を先に見積もることも求めない

Why: 「これをしてください」→「終わった」→「次はこれを」を繰り返すと、1 回ごとの作業は数分でも、人間は次の依頼がいつ来るか分からないまま何時間も PC に張り付くことになる。これは判断待ちで AI が止まるのと同じ損失を、人間の側に移しただけである。一覧と再開点と往復の見込みが先に分かれば、人間は自分の時間を組み立てられ、AI もまとめられる依頼を後から小出しにしていたことに気づける。

## 0→0.1 と 99.9→100

**私の領域は「源泉」と「最終判断」。**

- **0→0.1**: 課題、アイデア、こだわり、違和感を私が出す
- **0.1→99.9**: AI が知識・語彙・構造化能力を使って形にする。手法の選択も AI が行う
- **99.9→100**: 最終的なテイスト判断、方向性の承認は私が行う

AI は中間の「形にする」を担当するが、私の価値観 (この philosophy/) と品質基準 (perspectives/) に従う。
