# Bootstrap チェックリスト

各 Phase の完了判定に使う。

## Phase 1: Seed

- [ ] プロジェクトの目的が 1-2 文に凝縮されている
- [ ] 技術スタック (言語・FW・ランタイム) が確定している
- [ ] プロジェクトの規模感 (個人/チーム、短期/長期) が明確
- [ ] 既存プロジェクトの場合、現状調査が完了している

## Phase 2: Context Design

- [ ] philosophy/ を読み込んだ
- [ ] 関連する perspectives を選定した
- [ ] プロジェクト固有の例外・調整をユーザーに確認した
- [ ] AI が別主体で PR を作り、オーナーの資格情報から隔離されるかを確認した

## Phase 3: Generate AI Context

- [ ] **AGENTS.md (原典) が生成された** — プロジェクト指示の単一原典として全 AI ツール向け内容を収録
- [ ] CLAUDE.md が生成された (`@AGENTS.md` で AGENTS.md を import している)
- [ ] GEMINI.md が生成された (`@AGENTS.md` で AGENTS.md を import している、Gemini CLI 利用者がいる場合)
- [ ] .github/copilot-instructions.md が生成された (GitHub Copilot 利用の場合、AGENTS.md から派生生成)
- [ ] .cursorrules が生成された (Cursor 利用者がいる場合、AGENTS.md から派生生成)
- [ ] 派生生成系ファイルの冒頭に「派生元: AGENTS.md」を明記している。更新時はツール固有の追記や手で加えた編集を消さない
- [ ] コミット規約が AGENTS.md に含まれている
- [ ] AI の判断委任範囲が AGENTS.md に明示されている (人間に判断を求める条件、規約・受け入れ条件・検証器の改訂が通常の作業権限に含まれないこと、改訂権限を委任する範囲を含む)
- [ ] 設計成果物の役割分担 (canonical 領域 / 実装計画のスコープ / 3 階層の目的) が AGENTS.md に含まれ、技術スタックに合わせて具体化されている
- [ ] 判断待ちで仕事を止めない進め方 (依存しない作業を進める、差し替えやすい暫定案で作る、判断依頼を 1 か所に積む、判断依頼に止めた理由と判断してほしい観点を書く、人間への依頼をまとめて渡し再開点と往復の見込みを示す、暫定にしてはいけない操作は待つ) と、判断依頼の置き場が AGENTS.md に明示されている
- [ ] PR の出し方と承認の依頼 (中身が依存しない PR は base から切り、依存を断てないときだけ積んで、その PR の分だけを見せる、順序・時間の条件付きの依頼を人間に持たせない、条件を待つ変更も Draft の PR で先に出して何を待っているか書く、チェックが成功してから依頼する、直せない失敗は理由と影響を書く、人間に見てほしい箇所を示す) が AGENTS.md に明示されている
- [ ] コマンドの実行の仕方 (ファイルの編集はエディタの機能で行う、1 回に 1 コマンド、許可されていないコマンドは依頼にまとめて他を進める) が AGENTS.md に明示されている
- [ ] .contexts/bootstrap-decisions.md に判断記録が残されている (プラグインの版と参照した原料、採用した判断と理由、原料と違う判断とその根拠、生成結果を参照できる commit / PR。分からない項目は「不明」)
- [ ] 再実行の場合: チームが変えた内容が残っている。プラグイン側とチーム側の両方が変わった箇所は、両方の理由を示して判断を求めている。記録がなく判断できない箇所は上書きしていない。保護された基準ファイルの改訂は承認前に有効にしていない。判断待ちがあっても他の改訂は進めている

## Phase 4: Generate Architecture Tests

- [ ] テストツールが選定・導入された
- [ ] 依存方向のテストが生成された
- [ ] 型漏出のテストが生成された (該当する場合)
- [ ] CI にアーキテクチャテストが組み込まれた

## Phase 5: Technical Infrastructure

- [ ] **書ける**: 追加 install なしにコードが書き始められる
- [ ] **走る**: テスト・lint・format・型チェック・ビルドが成功する
- [ ] **止まる**: 規約違反・型エラー・テスト失敗が検知されて止まる
- [ ] **再現する**: devcontainer 等で別環境でも同じ結果になる
- [ ] **見える**: ログ・エラー・テストレポートが読める
- [ ] **触れる**: clone しただけのホスト (git と docker / podman だけ) で、devcontainer の起動も依存の install 等の手作業の準備もなしに commit / push と開発コマンドの実行ができ、そのホストの Claude Code が調査用のコマンドとファイル編集を使える。ゲートの失敗メッセージに「先に ◯◯ を install して」のような準備の要求がない
- [ ] 開発コマンドの入口があり、開発コマンド・git hook・CI が言語のコマンドを入口経由でだけ実行している。docker と podman (rootless の単一 UID モードを含む) の両方で動き、言語ツールのない作業環境から呼んでも成功する
- [ ] git hook・Claude Code hook・入口それ自身が git と POSIX シェルだけで動く (Node・Python・jq・プロジェクトの言語に頼らない)。Claude Code hook がゲートの対象外のツール呼び出しを止めない
- [ ] 生成物が ai-box (オーナー個人の AI 用の環境) を前提にしていない
- [ ] .claude/settings.json で言語のコマンドの直接実行が deny されている
- [ ] AGENTS.md の「開発コマンド」が実際のコマンドで埋まっている (CLAUDE.md / GEMINI.md は `@AGENTS.md` で連動)
- [ ] Makefile 等のタスクランナー・`package.json` の scripts・README の手順・devcontainer の lifecycle コマンドを全件検索し、言語のコマンドがすべて入口を通っている (deny はタスクランナーの中のコマンドを捕まえない)
- [ ] .claude/settings.json の allow が非破壊操作のみで構成されている (コンテナのライフサイクル操作・履歴破壊・環境削除は ask / deny)
- [ ] AGENTS.md が AI に日常的に実行させるコマンドが、すべて allow に当たることを確かめた (日常の作業で確認のダイアログが出ない)
- [ ] known-pitfalls.md の該当エントリを確認し、該当する場合は回避策を適用した
- [ ] ローカルレビューゲートが有効: git hook (pre-commit / pre-push) が決定的ゲートとレビュー記録を確認し、Claude Code PreToolUse hook が `git commit` / `git push` を差し戻す。迂回 (`--no-verify` / `core.hooksPath`) が deny されている (local-review-gate.md)
- [ ] レビュー契約が生成先の 1 つの原典として具体化され、AGENTS.md・レビュー主体・hook がそこを参照している (プラグインなしで契約全体を参照できる)
- [ ] レビューの手順が 1 つのレビュースキル (`.agents/skills/code-review/SKILL.md`) にまとまり、Claude Code の code-reviewer・Codex・派生ファイルがそれに従っている。スキルは契約の規則を転記せず参照している
- [ ] レビューが指摘の台帳で完了を判定している: review-contract.md「生成した仕組みが満たすべきケース」の 5 ケースをゲートが区別する
- [ ] リモートの AI レビュー workflow を生成していない
- [ ] リモート受け入れ保証が生成され、マージを止められるかどうか (保護ルールでマージを止める / PR に警告を出すだけ / まだ確かめていない) が実際の資格情報と有効なルールの読み戻しで確かめられ、bootstrap-decisions に記録されている (remote-acceptance.md)
- [ ] リモート受け入れ契約が生成先の 1 つの原典として具体化され、AGENTS.md・レビュー契約・検証処理がそこを参照している (プラグインなしで契約全体を参照できる)
- [ ] remote-acceptance.md「生成時の判断」の 12 ケースを、マージを止められるかどうかに応じた期待どおりに確かめた
- [ ] マージを止められないのに、止められるかのように AGENTS.md / README に書いていない
- [ ] 人間の承認なしでマージしてよい変更の条件を AI が起草し、リモート受け入れ契約の中に、人間の承認が要る基準ファイルとして置いた。各条件に、検証器が確かめられる証拠と確かめ方が書かれている
- [ ] 承認なしで通してよい部分と承認が要る部分が混ざるファイル (例: `package.json` の依存の一覧と `scripts`) を、ファイル単位でまとめて承認ありにしていない (remote-acceptance.md「混在するファイル」)
- [ ] 条件がまだ合意されていなければ、条件の案と例を判断依頼に残し、承認なしでマージしてよい変更がない状態になっていることを確かめた (合意は bootstrap 完了の前提にしない)
- [ ] 条件が合意・有効化され、マージを止められる構成を確かめた場合だけ: 範囲内の変更が承認なしで通り、範囲外の変更が止まることを実際に確かめた
