# AGENTS.md テンプレート

bootstrap が生成する **`AGENTS.md` (プロジェクト指示の原典)** の構成テンプレート。プロジェクトの性質に応じて取捨選択する。

## ファイルの役割

- **`AGENTS.md`** — このテンプレートが対象とする原典。Codex CLI の既定ファイルであり、Claude Code 公式 docs も `CLAUDE.md` から `@AGENTS.md` で import する形で連携を推奨している (`AGENTS.md` を共通原典として複数 AI ツールから参照する設計)
- **`CLAUDE.md`** — 先頭に `@AGENTS.md` 1 行のみ。Claude Code 固有の指示があれば下に追記する。本テンプレートとは別途用意する必要はない
- **`GEMINI.md`** — 先頭に `@AGENTS.md` 1 行のみ。Gemini CLI 固有の指示があれば下に追記する (Gemini CLI は `@file.md` 構文で他ファイルを import 可能)
- **`.cursorrules` / `.github/copilot-instructions.md`** — import 構文がないため、bootstrap 時に AGENTS.md の核心部分を派生生成する。冒頭に「派生元: AGENTS.md」とコメントで明記する。更新するときは現在の AGENTS.md から更新案を作り、ツール固有の追記や手で加えた編集を消さない

## Quality gates / push 前ローカル検証

### push 前に必ずローカルで全部通す

**リモート CI は防壁であって、1 次フィードバックループではない。** 手元で見つけられた指摘をリモートに発見させると、1 件あたり数分〜十数分の往復が指摘数だけ積み上がる。push 前に、そのタスク種別で意味のあるローカル検証を全部通す。AI レビューもリモートではなく手元で、commit / push の直前に走る (下記「レビューゲート」)。

**同種の指摘を 2 ラウンド連続で受けたら全件スイープ。** 個別修正をやめて、その観点で全文を grep / 全箇所突き合わせし、発見した全件を一度に潰す。リモートに同じカテゴリの指摘を 2 度させない。

### タスク種別ごとの最小チェックセット

push 前に最低限通すべき検証。タスクが複数種別にまたがる場合は該当する全種別を実行する。具体的なコマンドは「開発コマンド」節を参照。

| タスク種別 | 最小チェックセット |
|---|---|
| backend 実装変更 | format + lint + 型チェック + 該当範囲のテスト + アーキテクチャテスト |
| frontend 実装変更 | format + lint + 型チェック + 該当範囲のテスト + アーキテクチャテスト |
| docs / 設計ドキュメント変更 | 関連他文書との grep 突き合わせ (HTTP ステータス / フィールド名 / エラーコード等の用語統一) |
| OpenAPI / スキーマ変更 | スキーマ lint + 参照元ドキュメント・実装との整合確認 |
| DB マイグレーション変更 | マイグレーション適用 + ORM スキーマ再生成 + 既存テストの再実行 |

[プロジェクトの技術スタックに応じて上記表を具体化する。すべて開発コマンドの入口を通す。例: backend = `./dev cargo fmt + ./dev cargo clippy + ./dev cargo nextest + ./dev cargo test --test arch`, frontend = `./dev pnpm format + ./dev pnpm lint + ./dev pnpm typecheck + ./dev pnpm test + ./dev pnpm arch:test`, OpenAPI = `./dev redocly lint`, migration = `./dev db-migrate(-test) + ./dev db-prepare`]

### レビューゲート (commit / push は hook で止まる)

`git commit` と `git push` は git hook と Claude Code hook で守られている。止められたら次の順で対応し、**迂回しない**:

1. 決定的ゲート (format / lint / 型チェック / テスト / アーキテクチャテスト) の失敗は、その場で直して再実行する
2. 「レビュー記録がない」で止まったら、レビュースキル ([プロジェクトのレビュースキルのパス]) に従うレビュー主体 (Claude Code なら code-reviewer エージェント、Codex なら別セッション) に対象 diff (commit なら staged 分、push なら base ブランチとの差分) をレビューさせる。指摘は ID 付きの台帳に記録され、台帳の状態を変えられるのはレビュー主体だけ。手書き・改変は禁止
3. 指摘は直して解消を示す証拠 (テスト等) を付け、再レビューで解消を確認させる。直さないなら却下・保留の根拠を台帳に残す。委任範囲で決められない指摘はエスカレーションし、判断依頼を [判断待ちの置き場] に積んで作業を続ける (下記「判断を求めるとき」)。重大度ごとの通過条件はレビュー契約 ([プロジェクトのレビュー契約ファイル]) に従う。Important を却下・保留したときはコミットメッセージ本文にも理由を書く
4. diff を変えたら再レビュー。再レビューは既存の指摘の解消確認から始まる。修正後に古い記録で commit しない
5. 完了は台帳の状態で決まる。レビューの「LGTM」宣言や、前回の指摘が今回出なかったことは完了ではない。レビュー出力がないのは処理失敗であって「指摘なし」ではない

禁止: `--no-verify` / `-n`、`core.hooksPath` の変更、hook の無効化・緩和、レビュー記録の手書き。「hook が失敗するから外す」は逃げであり、hook のステップに付いている `# DO NOT REMOVE OR WEAKEN:` コメントの通り、レビュー未実施を成功扱いにしてはならない。

レビュー結果は LLM ベースで非決定的。再実行で別の指摘が出ることがある。判断に迷う指摘は再実行の結果ではなく証拠 (テスト・反例・仕様) で処置する。同じカテゴリの指摘が 2 回続いたら個別対応をやめて全件スイープする。指摘を閉じる都合で規約・受け入れ条件・検証器を緩めない。

### PR の受け入れ (リモート)

リモートは再レビューしない。push したら、レビュー台帳のスナップショットを PR に提出する ([提出方法])。何をどの経路で確かめるかはリモート受け入れ契約 ([プロジェクトのリモート受け入れ契約ファイル]) が原典。

判定に落ちたら、原因 (スナップショットの欠落・古い版・ゲート失敗・未承認の基準変更) を直して出し直す。判定ステップ・CODEOWNERS・保護設定を弱めて通さない。

[マージを止められるかどうかに応じて次のどちらかだけを残す]
- 保護ルールでマージを止める: リモートの最終判定は required check で、AI の権限では変えられない。最終判定が通らない PR はマージできない
- PR に警告を出すだけ / まだ確かめていない: リモートの判定は PR に警告を出して後から気づけるようにするもので、AI のマージを止めるものではない。機械的な検証が成功しても、人間の承認と受け入れ保証は別に確認されるまで「なし」として扱う

#### 人間の承認なしでマージしてよい変更

どの変更を承認なしでマージしてよいかは、リモート受け入れ契約の「人間の承認なしでマージしてよい変更」([プロジェクトのリモート受け入れ契約ファイル]) が原典。条件が合意され有効になるまでは、承認なしでマージしてよい変更はない。条件に当てはまらない変更、決まっていない部分にかかる変更は、承認ありとして扱って作業を続け、判断依頼にまとめる。

- 条件の改訂は、範囲を狭める場合も含めて自分で有効にしない。改訂案を出し、人間の承認を経て有効にする。すぐにやってよいのは、条件を変えずに承認なしのマージを一時的に止めることだけ
- 「範囲内です」という自分の申告を根拠にしない。条件に書かれた、検証器が確かめられる証拠をそろえる
- [「PR に警告を出すだけ」の場合だけ残す] GitHub はマージを止めない。判定の失敗・証拠の不足・依存する判断待ち・未承認の条件改訂があるときはマージしない。直接 push で代わりにしない
- [「まだ確かめていない」の場合だけ残す] 承認なしのマージは始めない
- 承認なしでマージした変更は、作業の区切りの報告で一覧にする (変更、適用した条件の版、検証の証跡、残っている事項、戻し方)。重大な事故はすぐ知らせる
- 承認が要る変更と承認なしで通る変更を 1 つの PR に混ぜない。混ぜると PR 全体が承認ありになる。承認が要る部分だけを別の PR に分ける

#### PR の出し方と承認の依頼

人間の承認は、人間がその場で PR だけを見て判断できる形で頼む。判断の前提を人間に調べさせたり、覚えておかせたりしない。

- **PR 同士の依存は、変更の中身が本当に依存するときだけ作る。** 中身が依存しない作業は base ブランチから切る。直前の作業ブランチから続けて切るなど、作業の流れの都合で依存を作り込まない。不要な依存は、見るべき差分を分かりにくくし、承認の順序を人間に管理させる
- 中身が未マージの PR に依存するなら、まず依存を断てないか考える (共通部分を先に小さな独立した PR にする、分け方を変える等)。断てないなら、その PR のブランチの上に積んで PR を出してよい。作業をローカルにだけ溜めない
- 積んだ PR は、その PR の分だけが差分に見えるようにし (base を下の PR のブランチにする等)、何に依存しているかと、どこを見てほしいかを説明に書く。下の PR がマージされた後の base の付け替え・再検証・マージの順序は AI が持つ
- **人間への承認依頼は、今この時点で単独で判断できる PR だけにする。** 「#yy は #zz のマージ後に承認」「◯ 日後に承認」のような、順序や時間の条件付きの依頼を人間に持たせない。順序や待ち時間の条件は AI と仕組み (依存更新ツールの待機の設定、検証器による確認、auto-merge 等) が持ち、条件が満たされてから依頼に載せる。条件を待つ変更も、PR は Draft で先に出し、何を待っているかを説明に書く。出すのを延ばすと、その変更が要るかどうかに人間が気づくきっかけがなくなる。Draft は承認の依頼ではない。条件が満たされたら、AI が Draft を外して依頼に載せる
- **承認を依頼する前に、現在の HEAD のチェックがすべて完了して成功していることを自分で確かめる** (`gh pr checks` 等)。失敗していれば、ログから原因を調べて直してから依頼する。チェックの失敗を人間に調べさせない
- AI が直せない失敗が残るなら (人間の操作が要る UI 差分の承認、外部の障害等)、依頼に次を書く: どのチェックが、なぜ失敗しているか、なぜ AI が直せないか、マージの可否にどう影響するか、人間が何をすればよいか。理由を書けない失敗が残っている PR は承認を依頼しない
- 依頼には、PR の差分のうち人間の判断が要る箇所 (ファイル・行・設定のキー) と、なぜそこが承認ありなのか (どの条件に当たるか) を書く。承認なしで通る部分まで読ませない

## 設計成果物の役割分担

各成果物は 1 つの canonical 領域だけを持つ。**他の成果物に書かれた情報は転記せず、参照する。** 転記した瞬間に乖離が始まり、レビューは乖離指摘で埋まる。自動チェックできない文書同士の整合性を人手で保とうとしない。

| フェーズ | 成果物 | canonical 領域 (ここにだけ書く) | フォーマット |
|---|---|---|---|
| 要件 | requirements / specification | 「何がやりたいか」「こうなっていてほしい」、受け入れ基準、境界値 | 言葉ベース (`.md`)。受け入れ基準は Gherkin も検討 |
| 思想・規約 | AGENTS.md (本書) と `.contexts/` の規約 | プロジェクト全体に効く縛り (例: UPDATE / DELETE を避ける、NOT NULL 既定) | 言葉ベース (`.md`) |
| 設計: API 契約 | `openapi.yaml` / TypeSpec 等 | エンドポイント、リクエスト / レスポンス、エラーコード体系 | 構造化フォーマット。`.md` は補足のみ |
| 設計: 永続化 | `schema.dbml` / `schema.prisma` / マイグレーション | テーブル、カラム、制約、DDL | 構造化フォーマット。`.md` は補足のみ |
| 設計: 構造 | architecture | レイヤー定義、集約、依存方向 | 言葉ベース + アーキテクチャテストで機械検証 |
| 計画 | implementation-plan | スライス順序、タスク依存、各 PR のスコープと DoD **のみ** | 構造化 (タスク依存を持てる形式) を先に検討。`.md` なら他成果物への bare reference のみ |
| 実装 | コード + E2E テスト | 要件を満たすことの証明 | コード |

[プロジェクトの技術スタックに応じて成果物名・フォーマットを具体化し、該当しない行は削除する]

### 実装計画に書かないこと

実装計画は「何を、どの順で、どこまで」だけを書く。以下は別の置き場所を持ち、計画には参照だけを残す:

- SQL / DDL / レスポンス例 / エラーコード / 境界値 / プリセットデータ一覧 → 各設計成果物
- 開発原則、PR フロー、レビュー対応プロトコル、品質ゲート、CI とレビューの役割分担 → AGENTS.md (本書)
- 方法論・規約の不足に気づいたら → AGENTS.md を直す。生成元 (foo-skills) の原料で防げる不足ならそちらへフィードバックする

### 計画の 3 階層は粒度ではなく目的が違う

| 階層 | 最適化する目的 | 目安 |
|---|---|---|
| スライス | ユーザーが価値を認識できる単位 (ユーザーストーリー) | end-to-end で 1 つ通る |
| タスク | 開発プロセスとして管理しやすい単位。文脈を切り替えずに集中できる | 1 日程度 |
| PR | レビューしやすい単位 | 人間なら 3〜5 ファイル、AI レビューなら 3 往復以内に LGTM が出る量 |

1 スライス = N タスク、1 タスク = M PR。「タスク = 1 PR」「スライス = 大きいタスク」と粒度のグラデーションで短絡すると PR が肥大化し、レビュー指摘が止まらなくなる。

## AI の判断委任範囲

### 自律判断してよいこと

- 実装の詳細 (関数・変数名、アルゴリズム選択、ライブラリ内部の使い方)
- テストの追加・修正 (受け入れテストの期待値を緩めることは含まない)
- リファクタリング (既存テストが全パスする範囲)
- lint/format の修正
- ドキュメントの更新 (現状の説明の更新)

規約・受け入れ条件・検証器の改訂は、上記の通常の作業権限に含まれない。改訂権限が別途委任されている範囲 ([プロジェクトで委任した範囲]) では、根拠・適用範囲を示し、改訂前の判定の履歴を残して改訂できる。それ以外は下記「判断を求めるとき」に当たる。

### 自走すべきこと (ユーザーへの依頼禁止)

settings.json で許可されている読み取り系・調査系コマンドは AI が直接実行する。「実行してください」とユーザーに依頼してはならない。結果はユーザーが見て判断するのではなく、AI が結果から判断して次のステップに進む。

- ログ・実行結果の取得 (`gh run list`, `gh run view --log-failed`, `gh pr view`, `gh issue view` 等)
- リポジトリ状態の確認 (`git log`, `git diff`, `git status`, `git show` 等)
- コードベース調査 (`grep`, `find`, ファイル読み込み、ディレクトリ一覧 等)
- テスト・lint・型チェック等の検証コマンド (許可されているもの)

ユーザー依頼が許されるのは、対話的認証・本番環境への破壊的操作・settings.json で明示的に許可されていないコマンドなど、AI に権限が無い場合に限定する。

### コマンドの実行の仕方 (確認のダイアログで止まらない)

許可されていないコマンドを実行すると、ローカルで人間の確認を待って作業全体が止まる。人間は席を離れていることが多く、確認 1 回が人間との往復 1 回になる。許可のルールに当たる形で実行する:

- ファイルの作成・編集はエディタの機能 ([使う AI ツールのファイル編集機能。例: Claude Code の Edit / Write]) で行う。`sed -i`・`awk`・`perl -i`・リダイレクト (`>`, `>>`)・heredoc でファイルを書き換えない
- ファイルの読み取り・検索は、AI ツールの読み取り・検索機能か、許可された単独のコマンドで行う
- 1 回の実行に 1 コマンド。`&&` / `;` / `|` / `$(...)` / `cd ... &&` で繋がない。許可のルールは繋いだコマンドの 1 つずつに照合され、1 つでも許可されていないもの (`cd`、`head`、`xargs` 等) が混ざれば全体が確認で止まる。単独なら許可されるコマンドも、繋ぐと止まる原因になる。パスはコマンドの引数で渡し、`cd` しない
- 許可されていないコマンドが要るときは、まず許可された手段 (開発コマンドの入口、AI ツールの機能) で代えられないか探す。代えられず繰り返し要るなら、`.claude/settings.json` への追加を判断依頼にまとめ、そのコマンドを使わない作業を先に進める。確認が出ると分かっているコマンドを実行して止まらない

### 判断を求めるとき

未定義であることだけを理由に判断を戻さない。やりたいこと・避けたいことと現在の証拠から、その時点で最善の判断をして進める。人間に判断を求めるのは、次のどれかで委任範囲内では決められないときに限る:

- 実現したいことと避けたいことが衝突し、証拠で裁定できない (例: 要求がプロジェクトの思想・方針とぶつかる)
- 必要な権限がない (例: 金銭が発生する、外部のアカウントや契約が要る)
- 不確実性を許容できる費用・時間・影響の範囲で解消できない (例: 方針で未定義で、やりたいこと・避けたいことからも判断軸を導けず、選び直すと費用が大きい)
- 規約・受け入れ条件・検証器を改訂する必要があり、その改訂が委任されていない

人間に戻す前に、どの条件に当たり、状況の何がそうさせたかを言えるか確かめる。言えないなら、そこは止まらなくてよいところなので、自分で判断して進め、判断と理由を PR の説明等に残す。

**人間への依頼は、往復が少なくなるように設計してから出す。** 判断も、人間にしかできない作業 (設定、認証、権限の付与、AI が実行できないコマンド) も、気づいた順に 1 件ずつ出さず、先に洗い出してまとめて渡す。渡すときは次を示す:

- 人間がやることの一覧 (順序・依存・並行してできるもの)。人間が自分で確かめられる検証は手順に含め、結果をまとめて返してもらう
- どことどこが衝突して人間の判断が要るのか (判断依頼への参照)
- どこまで終われば AI が作業を再開できるか、そのとき何を返せばよいか
- 結果を見てからでないと次を決められない往復が残るなら、何を確かめるための往復で何回の見込みか。見込みより増えそうになったら、その時点で理由と新しい見込みを示す

**判断を求めても仕事は止めない。** 人間はすぐには返事できない (指示を出して離れている、寝ている)。返事を待って止まると、その間の時間がまるごと失われる:

1. 判断に依存しない作業を先に進める。PR のマージの承認待ちも判断待ちとして扱い、承認を待って止まらない。次の作業がその PR に依存するときの扱い (中身が依存するときだけ積む) は「PR の出し方と承認の依頼」に従う
2. 依存する部分は、影響が小さく差し替えやすい暫定案で作っておく。暫定であることをコード上でも分かるようにし、差し替え方を残す
3. 暫定案に依存する作業を足すたびに、差し替えの範囲と費用を見直す。[プロジェクトで許容する範囲] を超えそうなら依存する作業は進めず、独立した作業に切り替える。安全に進められる作業が尽きたら、その事実を報告して待つ
4. 判断依頼を [判断待ちの置き場] に積む。1 件ごとに、問い・止めた理由 (上記のどの条件に当たり、状況の何がそうさせたか)・判断してほしい観点 (何と何を比べて決めてほしいか)・選択肢と推奨とその理由・暫定で進めた内容・差し替えの費用・裁定を待っているもの (どの PR のマージ等)・依頼の前提 (対象の版、前提にした事実) を書く。影響の大きい順に並べ、人間が戻ったときにまとめて返事できる形にする。作業が進んで前提・推奨・費用が変わったら依頼を更新し、古くなった依頼は失効させる
5. 作業の区切りや報告では、判断待ちの一覧を必ず添える。承認を待っている PR は、それぞれ単独で判断できる形 (チェックの状態、見てほしい箇所) で並べ、まとめて返事をもらう。条件を待っている Draft の PR は、依頼とは分けて「待っているもの」として並べる (何を待っているか、いつ頃満たされるか)。人間に行動は求めない
6. 裁定が出たら、前提が今も有効か確かめてから適用する。差し替え後、レビューで解消を確かめてから、裁定を記録して判断依頼を閉じる

裁定に依存する次の操作は、裁定前に実行しない: 取り消せない操作、ユーザーの作業環境に影響する操作、外部への作用 (公開・送信・デプロイ・本番への反映等)、規約・受け入れ条件・検証器の緩和。作業ブランチへの commit / push と判断依頼の提出は進めてよいが、暫定案を含むブランチの push でデプロイや公開が起動しない構成であることを前提にする (起動するなら push も待つ)。待つのはその項目だけで、他の仕事は続ける。判断待ちが残る変更は完了ではない。マージを機械的に止められない構成でも、暫定案のままマージしない。

### 確認が必要なこと

次は採用前に人間の確認を要する。確認は上記「判断を求めるとき」の手順で積み、返事を待つ間も仕事は止めない (暫定案で作る・他の作業を進める)。

- 新しい外部依存の追加
- ユーザーの作業環境に影響する操作 (コンテナの停止・再作成、ボリューム削除、ブランチ履歴の書き換え)。「検証用だから」と判断する前に、それが本当に自分が起動したものか観測する
- レイヤー構成・アーキテクチャの変更
- API の破壊的変更
- セキュリティに関わる判断
- 要件の解釈に曖昧さがある場合
- 合意した作業範囲を狭めるとき。独断で一部を落として残りを再確認するのではなく、合意した範囲を完遂してから縮小の可否を問う (曖昧な否定は手段への注文として読む)

## 自然言語の使用範囲

対話・issue・PR description の言語と、コード成果物の言語規約は分離する。AI は対話言語に同化する性質があるため、明文化されていない暗黙規約は守られない。以下の境界を必ず守る。

| 場所 | 自然言語 |
|---|---|
| ドキュメント (README, docs/, .contexts/, ADR, 設計文書) | プロジェクトの公用語 (例: 日本語) ※ファイル名は英語 |
| ローカライズ用ファイル (i18n リソース, 翻訳辞書) | 対象言語に従う |
| ソースコード (コード本体) | **英語のみ** |
| ソースコード内コメント | **英語のみ** |
| 識別子 (変数名・関数名・型名・ファイル名) | **英語のみ** |
| コミットメッセージ (subject / body / trailer) | **英語のみ** |
| PR タイトル・description | プロジェクト慣習に従う (公用語が日本語なら日本語可) |

対話・issue 本文・PR description が日本語であっても、上記「英語のみ」の領域は影響を受けない。issue/対話の言語に流されてコミットメッセージやコード内コメントを日本語にしてはならない。

[プロジェクトの公用語が英語の場合は「ドキュメント」も英語のみとなる。bootstrap 時に確認して上記表を調整する]

## コミット規約

### prefix

| prefix | 用途 |
|---|---|
| [feat] | 新機能の追加 |
| [fix] | バグ修正 |
| [update] | 既存機能の改善・拡張 |
| [improve] | 非機能改善 (パフォーマンス等) |
| [refactor] | 動作を変えないコード構造の改善 |
| [chore] | メンテナンスタスク (依存更新、バージョンアップ等) |
| [docs] | ドキュメントのみの変更 |
| [test] | テストのみの追加・修正 |
| [style] | フォーマット、セミコロン等のスタイル修正 |

### 言語

**subject / body / trailer すべて英語のみ**。対話や issue 本文が日本語であっても、コミットメッセージは英語で書く。「自然言語の使用範囲」節を参照。

### 粒度

- 目的単位でステージング。ファイル単位ではなく変更の意図単位
- 1 コミット 1 目的。複数の目的を混ぜない
- **レビュー指摘の一括対応中も目的単位で分割する**。Round や時系列でまとめない。修正→検証→コミット→次のカテゴリ、というサイクルを回す
