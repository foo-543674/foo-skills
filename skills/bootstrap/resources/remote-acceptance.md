# リモート受け入れ保証の設計基準

bootstrap が Phase 5 で生成する「PR を受け入れてよいかをリモートで確かめる仕組み」の設計基準。workflow やスクリプトの書き方 (How) は置かず、何を誰の権限で確かめるか (What / When) と、その理由 (Why) を置く。

bootstrap は本書を生成先の **1 つの原典** (例: `docs/remote-acceptance.md`) として具体化し、AGENTS.md・レビュー契約・検証処理はそこを参照する。プラグインを外しても契約全体が生成先に残る状態にする。

**リモートはもう一度レビューする場ではない。** 欠陥を探すのは手元のレビューゲート (`local-review-gate.md`) の仕事で、リモートでは LLM を使わない。リモートの役割は、**実装エージェントの権限では変えられない検証経路で、対象の版が明示された受け入れ条件に適合していることを確かめる** ことに限る。

## なぜリモートか

手元の hook・台帳・検証基準は、実装しているエージェント自身が書き換えられる。手元のゲートが保証するのは運用の規律までで、改ざんへの耐性はない (`review-contract.md`「この契約が保証しないこと」)。破れない層は、エージェントの資格情報で変えられない場所にしか置けない。

## マージを止められるかは、置き場所ではなく AI の資格情報で決まる

検証をリモートに置いただけでは、AI のマージは止められない。AI がオーナーの認証 (admin 権限を含む) で動いていれば、ruleset も CODEOWNERS も AI 自身が外したり承認したりできる。マージを止められるのは、AI の資格情報で次のどれもできないときに限る:

- ruleset・保護設定の変更や迂回
- 人間の承認として数えられるレビューの投稿
- 受け入れ判定の結果の発行
- 上記の権限を持つ資格情報 (オーナーのトークン等) の読み取り

PR は AI 側の別の主体 (GitHub App / bot アカウント) が作り、人間の資格情報は AI から隔離する。権限を絞った PAT でも、オーナー本人の ID なら別主体にはならない。GitHub は PR 作成者による自己承認を認めないため、作成者がオーナー本人だと人間の承認が成立しない。

bootstrap は、リポジトリが次のどの状態かを `.contexts/bootstrap-decisions.md` に記録する。Phase 2 で希望する構成を決め、Phase 5 で実際の資格情報と有効なルールを読み戻して確かめる。

| 状態 | 意味 |
|---|---|
| GitHub の保護ルールでマージを止める | AI の権限では保護ルールを外せない。受け入れ条件を満たさない PR は、AI がマージしようとしても GitHub が拒否する |
| PR に警告を出すだけ | 受け入れ条件を満たさない PR には、チェックの失敗と警告を PR に出し、人間が後から見て気づけるようにする。AI がマージすること自体は止められない |
| まだ確かめていない | 実際の権限と有効なルールを読み戻していないので、上のどちらか分からない。「PR に警告を出すだけ」と同じに扱う |

AI 用の別アカウントが存在するだけでは「保護ルールでマージを止める」にしない。ホスティングのプランや公開範囲によって保護ルール自体が使えないことがある (例: GitHub Free の private リポジトリでは ruleset・ブランチ保護を設定できない)。その場合、別主体の権限を絞っても AI は base への直接 push や自分の PR のマージができるので、「PR に警告を出すだけ」とし、理由 (プランの制限) と、マージを止めるための選択肢 (プランの変更、公開範囲の変更、組織のリポジトリへの移動) を記録する。厳密な統制が要らないリポジトリ (個人の private リポジトリ等) では、「PR に警告を出すだけ」で足りることも多い。止められないのに、止められるかのように AGENTS.md や README に書かない。

## 何を確かめるか

| 確かめること | 根拠 |
|---|---|
| 決定的ゲート (format / lint / 型 / テスト / アーキテクチャテスト) が対象の版で **実行され成功した** | skipped・neutral を成功扱いにしない。required check の名前が緑なだけでは「実行された」ことにならない |
| 提出されたレビュー台帳のスナップショットが対象の版に対応し、`review-contract.md`「完了の判定」を満たす | スナップショットが無い・壊れている・版が合わない = 不合格。処理失敗を合格扱いにしない。エスカレーション中の指摘は手元の commit / push を止めないので、ここで初めて受け入れを止める |
| 対象の変更が依存する未裁定の判断依頼がない | レビュー指摘に由来しない判断待ちも含め、重大度に関係なく受け入れを止める。依存する判断依頼はスナップショットと一緒に提出させる。無関係な判断待ちでは止めない |
| 基準ファイルが変更されていれば、人間が承認している | 作業を通す都合で基準を緩める経路を塞ぐ (philosophy/development-values「意図から仕事を具体化する」) |

台帳について保証できるのは「記載された状態が契約の通過条件に適合する」までである。スナップショットは実装側が提出するので、書かれていない Critical や判断待ちが存在しないことや、解消理由が正しいことまでは保証しない。

## 信頼できる検証経路

- 受け入れ判定は **保護された既存の版** の検証器・契約で行う。PR が検証器を書き換えても、その PR の判定には効かない
- PR のコードを実行する CI と、証跡と承認を検証して最終結果を発行する処理を分ける。特権を持つ処理の中で PR のコードを実行しない
- 最終結果の発行処理は、必要な検証がすべて対象の版で実行され成功したことを自分で確かめる。入力として信頼する CI 結果は、保護された設定で定義した workflow・ジョブ・実行経路のものに限り、発行元・run・対象 SHA・使った workflow と検証器の版を照合する。同じ名前のチェックが成功しているだけでは信頼しない
- 「保護ルールでマージを止める」構成では、この最終判定を required check にする。不合格・欠落・未完了ならマージできない。required check にしない判定はマージを拘束しない
- 現在の対象の版 (HEAD・base・契約と検証器の版) に対応する成功がない間は、「保護ルールでマージを止める」構成ではマージできない。HEAD が変わらず base だけ進んだ場合も古い成功を使わない。これを成り立たせる方式 (base への追従を必須にする、マージキューで統合直前に検証する等) は生成時に選ぶ
- 判定ステップには `# DO NOT REMOVE OR WEAKEN:` で存在意義 (証跡なし・検証スキップを合格にしない) を書き残す
- 判定が不合格のときは、どの条件に落ちたか、なぜか、何をすれば通るかを判定結果 (チェックの要約) に書く。人間が PR の画面だけで、マージしてよいかと誰が何をすべきかを判断できるようにする。判定処理自体の不具合 (スクリプトのエラー等) で落ちたなら、それは受け入れ条件の不合格ではなく検証経路の故障として区別して出し、直す

## 証跡の対応付け

スナップショットには少なくとも次を含め、検証時に照合する:

- 対象のリポジトリと PR、HEAD の SHA
- base の SHA と差分の範囲の定義 (merge-base から HEAD まで、等)
- 適用した契約・検証器の版
- スナップショットの内容のハッシュ

HEAD・base・契約や検証器の版のどれかが変われば再検証する。PR 差分のレビュー証跡と、統合後の状態での CI 成功は別の証拠として扱い、どちらを検証したかを結果に残す。

提出方式は 1 つにする。既定は **PR コメントで提出 → 検証時に内容を固定 → CI の artifact に保存** する。PR コメントは編集できるので、検証に使った内容をハッシュとともに artifact に固定し、判定結果からそれを参照できるようにする。台帳をコミットに含めると、レビュー対象の差分そのものが変わってしまう。

## 保護する基準ファイル

CODEOWNERS で人間に割り当て、ruleset で code owner の承認を必須にする。CODEOWNERS は base ブランチ側の定義が使われるので、PR 内で書き換えても、その PR の判定は既存の定義で行われる。

- AGENTS.md、レビュー契約、リモート受け入れ契約 (承認なしでマージしてよい変更の条件を含む)、アーキテクチャテスト、git hook、CI の workflow と、そこから呼ばれるスクリプト・設定、`.claude/settings.json`、CODEOWNERS 自身
- 承認後に push されたら承認を失効させる (承認済みの PR に基準の変更を後から足す経路を塞ぐ)
- bootstrap の再実行による変更も基準の改訂として、同じ承認を経る

ファイル単位の保護は安全側に倒している。承認が要る部分と要らない部分が混ざるファイルは、ファイル単位で保護せず、検証器がキー単位で判定する (「混在するファイル」)。AGENTS.md の現状説明の更新や、アーキテクチャテストの強化にも承認が要るという手間が出るので、その手間を bootstrap-decisions に明記する。緩和だけを意味的に検出する仕組みはまだ持たない。

## マージを止められないとき

「PR に警告を出すだけ」「まだ確かめていない」でも、決定的ゲートの再実行・証跡の照合・artifact への保存は生成する。事故に後から気づくのに役立つ。ただし自己承認できない必須ルール (code owner の承認必須等) は機械的に有効化しない。作業が止まるだけで、AI のマージを止めることにはならないからである。

判定結果は「機械的な検証の結果」と「人間の承認・受け入れ保証の有無」を別の項目として出す。機械的な検証が成功しても、受け入れ条件をすべて満たしたとは表示しない。基準ファイルの変更があれば「人間の確認が必要、受け入れ保証なし」と出す。

どの状態でも、エスカレーション中の指摘と、対象の変更が依存する未裁定の判断依頼は、不合格の理由とは別に「人間の判断待ち」として依頼への参照とともに列挙する。人間が戻ったときに、何を決めればマージに進めるかがそこで分かるようにする。

## 生成時の判断

- ruleset はリポジトリの設定であってファイルにできない。bootstrap は ruleset の定義と適用手順を生成し、適用は人間の確認を経て行う (外部に影響する操作)。「生成済み / 適用予定 / 有効化済み」を区別し、適用後に読み戻して確かめる。既存のルールを丸ごと置き換えない
- Phase 5 の動作確認で、次が受け入れられないことを確かめる。「保護ルールでマージを止める」構成では 1〜12 がすべてマージ不可になる。「PR に警告を出すだけ」「まだ確かめていない」では 1〜5 が不合格と表示され、6 が「人間の確認が必要、受け入れ保証なし」と、10 が「人間の判断待ち」と表示され、11・12 では AI がマージしない:
  1. スナップショットが無い・壊れている
  2. HEAD が進んだ後の古いスナップショット
  3. 決定的ゲートの skipped・未実行
  4. Critical が未処置のスナップショット
  5. 定義外の workflow が出した同じ名前の成功チェック
  6. 人間の承認なしの基準ファイルの変更
  7. 承認後の push
  8. 最終判定の欠落・失敗
  9. HEAD は同じで base や契約の版だけが進んだ後の古い成功
  10. 対象の変更が依存する未裁定の判断依頼が残っている (レビュー指摘に由来しないものを含む)
  11. 「人間の承認なしでマージしてよい変更」の範囲外の変更を、人間の承認なしでマージする。AI は範囲内だと申告しているが、証拠が範囲外を示す、または証拠がない場合を含む
  12. 条件の改訂を、人間の承認なしで有効にする。範囲を狭めると説明している改訂を含む

## 人間の承認なしでマージしてよい変更

方針が決まった後の量の多い作業を、PR ごとに人間が承認していては、人間がボトルネックになる (philosophy/development-values「0→0.1 と 99.9→100」)。そこで、どの変更なら人間の承認なしで受け入れてよいかを、受け入れ契約の一部として持つ。別のファイルは作らず、この契約を具体化した生成先の原典に置く。

### 条件は AI が起草する

人間に網羅的な条件表を書かせない (philosophy/development-values「意図から仕事を具体化する」)。AI が次を材料に初案を作り、その時点で最善の判断として具体化する:

- 人間が語った「実現したいこと」「避けたいこと」と、その理由・前提
- AGENTS.md、要件・受け入れ基準、既存の設計判断
- CODEOWNERS と、実際に有効な保護設定
- テスト・監視・戻す手段で、実際に保証できる範囲
- 過去の見逃し・不具合・差し戻しと、その原因

条件には、承認なしで受け入れる範囲、人間の判断が要る変更、必要な証拠、戻し方の条件、条件を改訂できる人、見直すきっかけを書く。変更されたパスは判定の材料の 1 つで、「認証のディレクトリに触れていないから安全」のようにパスだけで決めない。

各条件には、保護された検証器が自分で確かめられる証拠と、その確かめ方を書く (変更されたパス、差分の大きさ、通ったテスト、生成物との一致など)。リモートは再レビューしないので、AI の「範囲内です」という申告は証拠にならない。検証器が機械的に確かめられない部分は、人間の承認が要る扱いにする。

最初の合意は、表を 1 行ずつ人間に確認させるのではなく、典型的な変更・危険な変更・判断が分かれそうな変更の例で、任せる範囲を確かめる形にする。網羅できるまで着手を待たない。

合意して有効にするまでは、承認なしでマージしてよい変更は 1 つもない。その間もすべての変更を承認ありとして作業を進め、条件の案は判断依頼にまとめる。決まっていない部分も同じ扱いにする。

#### 混在するファイル

1 つのファイルに、承認なしで通してよい部分と承認が要る部分が混ざることがある (例: `package.json` の依存の一覧と、CI が呼ぶ `scripts`。`Cargo.toml` の `[dependencies]` と `[lints]`)。これを「ファイルに承認が要る部分がある」としてファイル全体を承認ありに倒さない。そのファイルを触る変更のほとんどが人間に回り、承認なしの範囲が名目だけになる。

- 構造化されたファイル (JSON / TOML / YAML 等) は、検証器がパースして変更されたキーで判定する。承認が要るのは、承認が要るキーが変わったときだけにする
- 承認が要る部分を混在するファイルの外に出せるなら、出す (CI はマニフェストの `scripts` ではなく開発コマンドの入口を呼ぶ、lint 等の設定を独立したファイルに置く)。出せればファイル単位の保護 (CODEOWNERS) がそのまま効く
- どちらもできない部分だけを承認ありにし、その理由を条件に書く。「安全側に倒した」は理由にならない

#### 時間や順序の条件

「公開から ◯ 日たった版だけを入れる」「#zz のマージ後でなければ受け入れない」のような時間・順序の条件は、仕組みが持つ。依存更新ツールの待機の設定、検証器による公開日時や依存先のマージの確認、条件を満たしてから PR を出す等で満たす。条件を満たしていない PR を「◯ 日後に承認してください」と人間に渡さない。人間に渡すのは、その時点で判断できる PR だけにする。

### 条件の改訂

改訂案は AI が起草してよい。ただし、**条件の改訂を AI が自分で有効にしない**。範囲を狭めると説明する改訂も同じで、狭める変更に証拠の要件を緩める変更が混ざれば、実質的に範囲が広がるからである。条件は保護する基準ファイルとして扱い、既存の手続き (code owner の承認等) を経て有効にする。有効になった後、進行中の PR は新しい条件で判定し直してよいが、前の判定は消さない。

すぐにやってよいのは、条件を変えずに **承認なしのマージを一時的に止める** ことだけである (見逃しが出たとき等)。止めている間はすべての変更を承認ありとして扱う。再開は既存の条件の範囲で行い、条件を変えて再開するなら、その改訂に人間の承認を受ける。

### GitHub での強制と、AI の規律の違い

- 「GitHub の保護ルールでマージを止める」構成では、承認なしで通るかを、保護された既存の版の条件で required check が判定する。AI の「承認不要と判断した」という報告やラベルだけでは通さない。条件・契約・検証器自身は人間の承認が要る基準ファイルにする
- CODEOWNERS の対象外であることと、承認なしで通ることは同じではない。ruleset がすべての PR に承認を求めていれば、対象外のパスでも承認が要る。個人所有のリポジトリではパスごとの承認者指定が使えない場合もある。生成した構成で「承認なしの範囲の変更は通り、それ以外は止まる」ことを実際に確かめる
- 「PR に警告を出すだけ」の構成でも、事前に任された条件を AI が確かめてマージする運用はできる。ただし GitHub は止めないので、AI は判定の失敗・証拠の不足・依存する判断待ち・未承認の条件改訂を無視してマージしない。直接 push で代わりにしない
- 「まだ確かめていない」構成では、承認なしのマージを始めない。作業は続ける

### 承認なしで受け入れる変更に求めること

- 1 つの意図にまとまっていて、後続の変更への依存が限られている
- 戻し方・影響範囲が分かっている。git revert で戻せても、データの変更や外部への作用 (デプロイ、通知、送信) まで戻るとは限らない。それらが起きる変更は、起きることまで任された範囲に入っているときだけ承認なしにする
- 不具合が見つかったら、承認なしのマージを一時的に止められる

### マージ後に人間が把握できるようにする

承認なしでマージした変更は、一覧 (変更、適用した条件の版、検証の証跡、残っている事項、戻し方) にまとめて人間に報告する。事後の承認を待つ列ではなく、結果を把握するための一覧である。重大な事故は一覧を待たずに知らせる。

### 見逃しからの見直し

- 承認なしでマージした変更で見逃しが出たら、まず生成先に評価用の事例として残し、原因を「条件の不足」「検証の不足」「要求の誤解」に分けて対処する。思想側のルールをすぐ増やさない
- 「事故がなかった」だけで範囲を広げない。適用した回数、実際の影響範囲、観測した期間、検出できる能力を根拠に、改訂の権限を持つ人が広げる

### 作らないもの

変更ごとのリスクの点数化、実績からの自動的な範囲拡大、安全性を意味的に判定する汎用の分類器、マージ専用の別 App、条件を管理する専用の仕組み。まず既存の受け入れ判定を広げる。

## この段階で扱わないこと

レビューの真正性の保証 (独立したレビュアーの署名等)、複数の提出方式、基準の意味的な緩和の検出、リモートでの LLM レビュー。
