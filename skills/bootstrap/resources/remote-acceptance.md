# リモート受け入れ保証の設計基準

bootstrap が Phase 5 で生成する「PR を受け入れてよいかをリモートで確かめる仕組み」の設計基準。workflow やスクリプトの書き方 (How) は置かず、何を誰の権限で確かめるか (What / When) と、その理由 (Why) を置く。

bootstrap は本書を生成先の **1 つの原典** (例: `docs/remote-acceptance.md`) として具体化し、AGENTS.md・レビュー契約・検証処理はそこを参照する。プラグインを外しても契約全体が生成先に残る状態にする。

**リモートはもう一度レビューする場ではない。** 欠陥を探すのは手元のレビューゲート (`local-review-gate.md`) の仕事で、リモートでは LLM を使わない。リモートの役割は、**実装エージェントの権限では変えられない検証経路で、対象の版が明示された受け入れ条件に適合していることを確かめる** ことに限る。

## なぜリモートか

手元の hook・台帳・検証基準は、実装しているエージェント自身が書き換えられる。手元のゲートが保証するのは運用の規律までで、改ざんへの耐性はない (`review-contract.md`「この契約が保証しないこと」)。破れない層は、エージェントの資格情報で変えられない場所にしか置けない。

## 境界は場所ではなく資格情報で決まる

リモートに置いただけでは境界にならない。AI がオーナーの認証 (admin 権限を含む) で動いていれば、ruleset も CODEOWNERS も AI 自身が迂回・承認できる。境界が成立するのは、AI の資格情報で次のどれもできないときに限る:

- ruleset・保護設定の変更や迂回
- 人間の承認として数えられるレビューの投稿
- 受け入れ判定の結果の発行
- 上記の権限を持つ資格情報 (オーナーのトークン等) の読み取り

PR は AI 側の別の主体 (GitHub App / bot アカウント) が作り、人間の資格情報は AI から隔離する。権限を絞った PAT でも、オーナー本人の ID なら別主体にはならない。GitHub は PR 作成者による自己承認を認めないため、作成者がオーナー本人だと人間の承認が成立しない。

bootstrap は境界の状態を **境界あり / 可視化のみ / 未確認** のどれかで `.contexts/bootstrap-decisions.md` に記録する。Phase 2 で希望する構成を決め、Phase 5 で実際の資格情報と有効なルールを読み戻して確かめる。別 ID が存在するだけでは「境界あり」にしない。境界がないのに、あるかのように AGENTS.md や README に書かない。

## 何を確かめるか

| 確かめること | 根拠 |
|---|---|
| 決定的ゲート (format / lint / 型 / テスト / アーキテクチャテスト) が対象の版で **実行され成功した** | skipped・neutral を成功扱いにしない。required check の名前が緑なだけでは「実行された」ことにならない |
| 提出されたレビュー台帳のスナップショットが対象の版に対応し、`review-contract.md`「完了の判定」を満たす | スナップショットが無い・壊れている・版が合わない = 不合格。処理失敗を合格扱いにしない |
| 基準ファイルが変更されていれば、人間が承認している | 作業を通す都合で基準を緩める経路を塞ぐ (philosophy/development-values「意図から仕事を具体化する」) |

台帳について保証できるのは「記載された状態が契約の通過条件に適合する」までである。スナップショットは実装側が提出するので、書かれていない Critical が存在しないことや、解消理由が正しいことまでは保証しない。

## 信頼できる検証経路

- 受け入れ判定は **保護された既存の版** の検証器・契約で行う。PR が検証器を書き換えても、その PR の判定には効かない
- PR のコードを実行する CI と、証跡と承認を検証して最終結果を発行する処理を分ける。特権を持つ処理の中で PR のコードを実行しない
- 最終結果の発行処理は、必要な検証がすべて対象の版で実行され成功したことを自分で確かめる。入力として信頼する CI 結果は、保護された設定で定義した workflow・ジョブ・実行経路のものに限り、発行元・run・対象 SHA・使った workflow と検証器の版を照合する。同じ名前のチェックが成功しているだけでは信頼しない
- 「境界あり」では、この最終判定を required check にする。不合格・欠落・未完了ならマージできない。required check にしない判定はマージを拘束しない
- 現在の対象の版 (HEAD・base・契約と検証器の版) に対応する成功がない間は、「境界あり」ではマージできない。HEAD が変わらず base だけ進んだ場合も古い成功を使わない。これを成り立たせる方式 (base への追従を必須にする、マージキューで統合直前に検証する等) は生成時に選ぶ
- 判定ステップには `# DO NOT REMOVE OR WEAKEN:` で存在意義 (証跡なし・検証スキップを合格にしない) を書き残す

## 証跡の対応付け

スナップショットには少なくとも次を含め、検証時に照合する:

- 対象のリポジトリと PR、HEAD の SHA
- base の SHA と差分の範囲の定義 (merge-base から HEAD まで、等)
- 適用した契約・検証器の版
- スナップショットの内容のハッシュ

HEAD・base・契約や検証器の版のどれかが変われば再検証する。PR 差分のレビュー証跡と、統合後の状態での CI 成功は別の証拠として扱い、どちらを検証したかを結果に残す。

提出方式は 1 つにする。既定は **PR コメントで提出 → 検証時に内容を固定 → CI の artifact に保存** する。PR コメントは編集できるので、検証に使った内容をハッシュとともに artifact に固定し、判定結果からそれを参照できるようにする。台帳をコミットに含めると、レビュー対象の差分そのものが変わってしまう。

## 保護する基準ファイル

CODEOWNERS で人間に割り当て、ruleset で code owner の承認を必須にする。CODEOWNERS は base ブランチ側の定義が使われるので、PR 内で書き換えても、その PR の判定は既存の定義で行われる。

- AGENTS.md、レビュー契約、アーキテクチャテスト、git hook、CI の workflow と、そこから呼ばれるスクリプト・設定、`.claude/settings.json`、CODEOWNERS 自身
- 承認後に push されたら承認を失効させる (承認済みの PR に基準の変更を後から足す経路を塞ぐ)

ファイル単位の保護は安全側に倒している。AGENTS.md の現状説明の更新や、アーキテクチャテストの強化にも承認が要るという手間が出るので、その手間を bootstrap-decisions に明記する。緩和だけを意味的に検出する仕組みはまだ持たない。

## 境界が成立しないとき

「可視化のみ」「未確認」でも、決定的ゲートの再実行・証跡の照合・artifact への保存は生成する。事故の検出には役立つ。ただし自己承認できない必須ルール (code owner の承認必須等) は機械的に有効化しない。作業が止まるだけで境界にはならないからである。

判定結果は「機械的な検証の結果」と「人間の承認・受け入れ保証の有無」を別の項目として出す。機械的な検証が成功しても、受け入れ条件をすべて満たしたとは表示しない。基準ファイルの変更があれば「人間の確認が必要、受け入れ保証なし」と出す。

## 生成時の判断

- ruleset はリポジトリの設定であってファイルにできない。bootstrap は ruleset の定義と適用手順を生成し、適用は人間の確認を経て行う (外部に影響する操作)。「生成済み / 適用予定 / 有効化済み」を区別し、適用後に読み戻して確かめる。既存のルールを丸ごと置き換えない
- Phase 5 の動作確認で、次が受け入れられないことを確かめる。「境界あり」では 1〜9 がすべてマージ不可になる。「可視化のみ」「未確認」では 1〜5 が不合格と表示され、6 が「人間の確認が必要、受け入れ保証なし」と表示される:
  1. スナップショットが無い・壊れている
  2. HEAD が進んだ後の古いスナップショット
  3. 決定的ゲートの skipped・未実行
  4. Critical が未処置のスナップショット
  5. 定義外の workflow が出した同じ名前の成功チェック
  6. 人間の承認なしの基準ファイルの変更
  7. 承認後の push
  8. 最終判定の欠落・失敗
  9. HEAD は同じで base や契約の版だけが進んだ後の古い成功

## この段階で扱わないこと

自動マージの条件 (変更のリスク分類)、レビューの真正性の保証 (独立したレビュアーの署名等)、複数の提出方式、基準の意味的な緩和の検出、リモートでの LLM レビュー。
