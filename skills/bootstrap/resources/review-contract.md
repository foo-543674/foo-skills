# レビュー契約の設計基準

bootstrap が生成するレビューの「指摘をどう扱い、何をもって完了とするか」の設計基準。レビューを誰が・いつ走らせるか (発火点) は `local-review-gate.md` が持ち、本書はレビューの中身の契約を持つ。記録のファイル形式やスクリプトの書き方 (How) は置かず、何を記録し何で完了を判定するか (What / When) と、その理由 (Why) を置く。

この契約はレビュー主体に依存しない。Claude Code の code-reviewer でも、Codex など他のツールでも、同じ契約で指摘を記録し処置する。

bootstrap は本書を生成先の **1 つの原典** (例: `docs/review-contract.md`) として具体化し、AGENTS.md・レビュー主体・hook はそこを参照する。判定規則を各所に転記しない。プラグインを外しても契約全体が生成先に残る状態にする。

## なぜ件数ではなく指摘の台帳か

- LLM レビューは非決定的。前回出た指摘が今回出ないのは「直った」とは限らず、「今回は見落とした」だけのことがある。件数だけの記録 (Critical 0 / Important 2) では両者を区別できない
- 件数で完了を判定すると、レビューを回すたびに判定を最初から取り直すことになり、「指摘 → 修正 → 新しい指摘」のループが終わらない。完了は個々の指摘の処置が積み上がった結果として決める
- 修正が新しい問題を生んだのか、前からあった問題を後で見つけたのかを区別できないと、ワークフローのどこを直すべきか分からない (修正時の制約確認が足りないのか、初回レビューの網羅性が足りないのか)

## 指摘が持つもの

| 項目 | 内容 |
|---|---|
| ID | 台帳の中で一意。同じ問題の言い換えは新しい ID を作らず、既存の指摘にまとめる |
| 対象 | ファイル・範囲と、レビューした版 (commit または diff ハッシュ) |
| 根拠 | 違反している要件・受け入れ条件・規約・設計原則と、それを示す証拠 (コード、再現手順、仕様の該当箇所) |
| 重大度 | Critical / Important / Minor と、その理由 |
| 状態 | 下記のライフサイクル |
| 処置の根拠 | 却下・保留・解消の理由と、それを裏付ける証拠 |
| 由来 | 修正が生んだ指摘なら、どの指摘への修正か。確認済み・推定・不明を区別し、不明を推測で埋めない |

## ライフサイクル

- **未処置** → **修正済み (未確認)** → **解消**: 解消の確認はレビュー側が行う。実装側は修正と、解消を示す証拠 (追加したテスト等) を付ける
- **却下**: 誤検知・根拠不足。仕様・テスト・反例などの証拠で裁定する
- **保留**: 妥当だが今回の変更の受け入れを妨げない。別タスクとして記録する。Critical には使えない
- **エスカレーション**: 委任された範囲では判断できない (意図の衝突、権限の不足、許容範囲を超える不確実性)。人間に判断を求める。人間の裁定が出るまで未処置と同じく扱う

解消・却下した指摘でも、新しい証拠や修正による再発があれば同じ ID で再開する。新しい証拠を示さずに同じ指摘を繰り返さない。

## 完了の判定

- 完了は台帳の状態と決定的ゲートの結果で判定する。レビュー主体の「LGTM」宣言は完了ではない
- Critical は「解消 (確認済み)」か「証拠付きの却下」だけが通る。未処置・修正済み (未確認)・エスカレーション中が 1 件でもあれば止める
- Important はすべてに処置 (解消・却下・保留) と根拠がある。エスカレーション中は止める
- Minor は任意
- レビューの出力がない・壊れているのは処理失敗であって「指摘なし」ではない。処理失敗を合格扱いにしない

## 再レビューの範囲

- 初回は変更全体を見る
- 2 回目以降は、既存の指摘の解消確認、前回からの差分、修正の影響範囲を中心に見る。新しい問題を見つけること自体は妨げないが、新規指摘は「前からあった見落とし」か「修正が生んだもの」かを由来に記録する
- 判断に迷う指摘は、再実行して残るかどうかではなく、証拠 (テスト・反例・仕様) で処置する。再実行で出なかったことは却下の根拠にならない
- 同じカテゴリの指摘が 2 回続いたら全件スイープ (philosophy/development-values)

## 基準の改訂

レビュー中に基準 (規約・受け入れ条件・検証器) の不適切さに気づいたら、改訂の提案は正当な仕事である。ただし philosophy/development-values「意図から仕事を具体化する」に従い、指摘を閉じる都合で基準を緩めない。改訂には根拠・権限・適用範囲を示し、改訂前の指摘と判定の履歴は消さない。

## 独立性

- 初回の独立評価には、承認済みの要件・制約・設計判断を渡し、実装時の思考の経緯・自己評価・説得のための説明は渡さない
- 解消確認では、変更内容・再現手順・検証結果を渡し、レビュー側が独立に確かめる。証拠は渡すが、結論は渡さない
- 同じ会話の中で自分の実装を自分でレビューしない

## 生成した仕組みが満たすべきケース

Phase 5 の動作確認で、生成したゲートが次を区別できることを確かめる:

1. 前回の Critical が今回のレビューで出なかった → 解消の確認がなければ止まる
2. 証拠付きで却下した Important → 止まらない
3. 解消済みの Critical が新しい証拠で再開した → 止まる
4. Critical をエスカレーションした → 人間の裁定が出るまで止まる
5. レビューの出力がない → 止まる (指摘なしとして通さない)

## この契約が保証しないこと

台帳は実装と同じエージェントが書き換えられる場所にある。この契約が保証するのは手元の運用の規律までで、改ざんへの耐性はない。実装エージェントの権限で変えられない受け入れ保証は、生成先のリモート受け入れ契約 (`remote-acceptance.md` から生成) が持つ。
